# commit-convention

只负责一次原子提交：检查 → 验证 → 审查 → 精准暂存 → 中文约定式提交 → 报告。发版、版本号、tag 与分支清理由 `release-workflow` 编排；其确定提交范围与时机后，可复用本技能完成原子提交，本技能不改变发版决策。

## 提交信息规范

前缀 + 具体中文描述。描述回答「做了什么」（why 入正文段，不在标题）。

| 前缀 | 用途 |
|------|------|
| `feat` | 新增功能、模块或业务逻辑 |
| `fix` | 修复 Bug，使失败测试通过 |
| `refactor` | 重构代码，不改变业务行为 |
| `test` | 新增或修改测试用例 |
| `docs` | 更新文档、规范或注释 |
| `chore` | 构建、依赖、版本等杂项 |
| `perf` | 性能优化 |
| `build` | 构建系统或外部依赖变更 |
| `ci` | CI 配置变更 |
| `revert` | 回滚某次提交 |

- 每个提交必须有具体、可读的中文描述，禁止无意义的「update」「fix bug」。
- 若一次提交涉及多个领域，选主导领域作前缀。
- `merge` 与 `chore(release)` 由 `release-workflow` 产生，不作为普通提交的默认选择。

## 执行流程

1. **状态检查**：`git status` 读取工作区变更文件列表。
2. **变更分析**：判断提交类型，按单一关注点分组（不同类型变更分多次提交）。
3. **信息生成**：按规范拼装 commit message（前缀 + 中文描述，why 入正文）。
4. **验证**：运行 `git diff --check` 检查已跟踪文件的差异，拦截尾随空白与文件末尾新增空行；随后运行匹配变更范围的测试/类型检查（按仓库验证路由，如受影响模块的 test 命令，命令清单见 scripts/gates.mjs）并确认通过。新文件与完整待提交内容的空白检查在第 6 步暂存后完成。
5. **审查**：见下方「审查」。
6. **精准暂存**：
   - 先运行 `git diff --cached --name-status` 和 `git diff --cached --patch` 审查已有暂存内容。若存在未明确纳入本次目标的文件或 hunk，必须停止，不得继续提交；只有用户明确确认扩大本次范围后，才能重新记录目标范围并继续。
   - 若目标文件已有与本次无关的暂存 hunk，不得用 `git add <文件>` 覆盖式暂存；应请求用户先拆分，或使用能保留既有 hunk 的逐块暂存方式，并重新审查完整 cached patch。不得擅自取消、覆盖或修改用户已有的暂存内容。
   - 范围确认后，执行 `git add <目标文件>`（按名添加），不用 `git add .` 或 `git add -A`；暂存后再次检查 `git diff --cached --name-status` 和 `git diff --cached --patch`，确认文件与 hunk 均只属于已批准范围，并运行 `git diff --cached --check`，失败时先修复并重新精准暂存。
7. **提交**：完成本技能前置检查、独立审查和精准暂存后，再次确认 cached 文件清单与 patch 仍符合已批准范围，仅提交已确认的暂存内容：`git commit -m "前缀(领域): 中文描述"`。该命令是本技能的正式步骤，不属于绕过技能流程的直接提交。
8. **报告**：简述提交内容、文件数、审查结论。
9. **提交后核验**：运行 `git diff-tree --no-commit-id --name-status -r HEAD`、`git status --short --branch` 和 `git log -1 --format=%h%x09%s`，将最新提交的文件清单与提交前已批准范围对照，确认最新提交信息正确，并确认剩余工作区变更仅为未纳入本次提交的内容；如需 hunk 级确认，再对照提交前审查过的 cached patch 与 `git show --format= --patch HEAD`。

## 独立审查

1. **必须由独立子代理审查**：主代理须在当前工作中直接派生一个未参与本次实现的临时子代理，并由该子代理完成审查后将结论返回主代理。与当前工作无直接派生关系的代理实例不能替代该子代理。
2. **必须隔离上下文**：审查子代理不得继承此前对话或实现过程，只能接收固定审查提示词规定的需求、待提交范围、约束和验证记录。
3. **必须完整使用固定提示词**：每轮审查前读取 `skills/commit-convention/references/review-prompt.md`（审查提示词），填写其中全部审查输入，并将完整正文交给审查子代理；不得附加主代理的自审结论或预期答案。
4. **无法满足即停止提交**：执行环境不能同时保证“由子代理审查”和“上下文隔离”时，报告阻塞；主代理自审不能替代独立审查。

必须等待审查完成后才能提交：仅 `PASS` 放行；`FAIL` 须先修复，`BLOCKED` 须先补齐核查条件。提交报告应包含最终审查结论及阻塞项处置结果。

### 复审触发与豁免

为避免同一提交被反复整轮审查、拖低效率，按改动性质区分是否需要重新审查：

- **须重新审查**：待提交范围、代码行为、工具／接口契约、配置、数据或文档结论发生实质变化时，原审查结论立即失效，须重新派生一个未参与实现、未参与此前审查且上下文隔离的子代理，完整复审最终内容。
- **免二次审查**：仅为非逻辑性、非阻塞改动——错别字、标点、排版、空白、纯措辞润色、等价改写，以及把链接改为名称一类不改变事实与结论的引用写法调整——时，不使原审查结论失效，无需重新派生审查者；主代理在提交报告中说明改动性质并沿用原结论即可。
- **边界与防滥用**：改动只要触及此前审查指出的阻塞项、改变审查覆盖范围（新增／删除文件、改变逻辑或结论），或无法确定是否属非逻辑性改动时，一律按「须重新审查」处理，不得借豁免条款降低放行标准。

## 多文件提交策略

- **单一关注点**：一次提交只含同一类型变更；feat 与 fix 并存时分两次提交。
- **原子化**：跨层变更按步骤拆分——先数据/模型（`feat`），再测试（`test`），最后表现层（`feat`）。
- **关联合并**：同一功能的数据模型 + 业务逻辑可合入一次 `feat`。

## 注意事项

- 提交前确认所有变更文件已保存；严禁提交含密钥/Token/密码的文件。
- git config 首次设置（编码/分页）见 AGENTS.md「Git 环境」段（仓库约定，不依赖用户级规则），本技能不处理。
- 若项目有 pre-commit hook，确保提交能通过。
