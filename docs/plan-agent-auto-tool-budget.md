# Chat auto 工具循环与每题积分预算实施计划

> 创建日期：2026-09-05
> 状态：施工中（代码实施完成，阶段 6 质量核查待完成）

## 目标

使用现有 Chat Completions 和本地工具，以固定 `tool_choice=auto` 完成一次真实用户提问、若干批工具往返及最终 `assistant.content`；由 Agent 决定取证顺序和结束时机，宿主按每题默认 5 点预算准入工具调用，并保留仅针对未调用工具就直接作答的一次回馈兜底。

一次用户提问从开始到最终回答是一个 session，内部模型生成步骤不另算用户 session。每次新提问都重置预算；工具结果或兜底消息不重置预算。

## 非目标

本计划不迁移 Responses 或 Anthropic Messages，不引入 MCP、Agent SDK、作答工具或服务端工具执行。流式输出、显式缓存、证据压缩、检索排序调优和游戏事实修订独立处理。

## 架构分析

当前 `bench/src/provider.ts` 已使用 Chat 和 `auto`，能解析整个 `tool_calls` 数组，但未显式发送 `parallel_tool_calls`。`bench/src/agent.ts` 使用固定 `maxRounds=3` 加一次清空工具的末轮；检索上限另由 `MAX_RAG_CALLS=2` 控制。未达到 `minRagCalls` 就作答时，宿主丢弃该正文并追加程序化 user 催检索，轮次控制和工具预算混在一起。

现有 tools 按模式选择 `rag_search`、`grep_search`、`lookup`、`query_operators`。工具执行及结果回写逐个进行，预算判断散落在分支内；`toolRounds` 记录含工具的模型批次，不能代表并行后的调用次数。`runner.ts` 只在 `runQuery` 成功返回后收集费用，异常路径会漏掉该题已经完成的模型调用。

前期同模型探针已验证：统一 schema 配合固定 `auto`，既可同批提出多个独立查询，也可读取结果后再决定下一次查询，最后返回原生正文。Chat `required` 和百炼 Messages `any` 在连续三步对照中均持续返回工具调用，相同历史的 `auto` 则可以作答。因此采用 Chat 固定 `auto`；强制首检改为指令及受限回馈兜底，不再宣称 API 保证首检。

## 实施方案

### 1. 固定执行契约与配置

输入为本计划及现有 `BenchConfig`、`AgentOptions`、`AgentResult`；输出为所有模块共用的预算、结束状态和参数口径。

| 项目 | 定稿规则 |
|---|---|
| API 与策略 | 继续 Chat Completions，全程 `tool_choice=auto`，包括回馈后及预算归零后 |
| 工具定义 | 延续统一 `knowledge` schema；一次调用只选择一个检索 operation |
| 并行 | Qwen 显式发送 `parallel_tool_calls=true`，宿主处理完整调用数组；模型可自行只提出一个调用 |
| 初始预算 | `toolBudget=5`，每次真实提问重置，所有操作共享 |
| 正常结束 | 响应无工具调用、正文非空且未截断，并通过未调用工具的回馈判定 |
| 预算未用满 | 允许提前回答，不要求用完积分 |
| 预算用尽 | 工具继续声明，超额请求只返回工具结果形式的作答提示 |
| 伪装 user 回馈 | 仅在本题从未提出工具调用却直接输出非空正文时触发，每题最多一次 |
| 异常边界 | 整题总超时或取消可中止执行，保留部分记录并标记未完成 |

在 `config.ts` 中用 `toolBudget` 替换 `maxRounds` 及硬编码的 `MAX_RAG_CALLS`；增加 `sessionTimeoutMs`，默认 300,000 毫秒，以及默认开启的 `feedbackOnNoToolAnswer`。积分和总超时均校验为正整数。CLI 增加 `--tool-budget N`、`--session-timeout-ms N`，不从实验环境变量隐式读取。

取消 `minRagCalls` 的次数下限语义。为现有实验入口保留 `--min-rag 0|1` 的兼容映射：0 关闭回馈，1 启用一次回馈，其他值明确报错；修复当前用 `Number(...) || null` 导致 0 被吞掉的解析。CLI 提示改称“未调用工具作答回馈”，不再称“强制首检”。默认正式路径保持回馈开启。

单题状态至少保存 `limit`、`used`、`requested`、`denied`、`executed`、`feedbackUsed`、模型步骤数和终止原因。余额由 `limit-used` 得到，始终满足 `0 <= used <= limit`。不以模型请求、工具批次或检索命中数扣点。Hy3 保留现有协议参数映射；未实测的并行请求参数不直接套用，完整调用数组的本地处理可共用。

验收：配置默认值、CLI 正负例及运行快照一致；循环不再读取旧轮次上限，两个独立问题各自从 5 点开始。

### 2. 先补齐异常记录和整题取消

输入为单题状态与当前 provider/runner 的失败路径；输出为正常、失败、中止都能保留已发生记录的结果契约。该步骤是移除固定轮次上限的前置条件。

扩展 `AgentResult`，明确完成状态、终止原因及失败信息；可预期的请求失败、工具系统故障、超时、取消、空响应或截断均携带截至当前的 `records`、真实步骤数、预算和证据统计返回。`runner.ts` 统一收集成功和失败结果，不再把失败题的步骤、工具序列和已有证据强制清零。失败说明由展示层渲染，`finalAnswer` 保持空值；已有但未被接受的模型正文留在 trace 中。

每个响应先保存可观察的 usage 和费用状态，再检查截断与协议完整性，通过后才能预占积分、执行工具或接受最终正文；被回馈拦下的正文也完整计费。provider 保留 HTTP 请求尝试、重试和等待信息；未收到 usage 的网络失败，以及 HTTP 200 但 usage 缺失、不完整或无效，均记录用量未知或部分未知，不能当作已确认零费用。

输入、输出计费用量必须分别校验为非负有限整数，明确返回的 0 有效，缺失、null、负值及非数值不能补成 0。可选缓存/思考明细仅在接口契约明确允许缺省为 0 时沿用该默认值；显式无效值仍须标记。保留有效部分并计算可确定的费用分项，其余用空值及完整性状态表达；整题和整批汇总展示已知费用小计与费用不完整标记，不能把小计标作完整总费用。仅 usage 不完整而正文/工具协议有效时可以继续执行，不为补齐统计自动重试模型请求。

总超时从单题开始计时，覆盖限流等待、请求、响应读取、重试退避、工具执行和后续模型步骤。通过取消信号贯穿 `provider.ts`、`rate-limiter.ts` 和可异步的工具执行器；现有单次请求 120 秒超时仍生效，但整题取消后不再重试或启动新请求。同步检索在边界检查信号，不宣称可以中途抢占同步 CPU 工作。

总超时是异常中止措施，不触发额外回答请求、切换 `none` 或增加 user 指令。运行结束后释放定时器和监听器。dry 路径使用同一生命周期，但不发网络请求。

验收：至少一次模型响应成功后发生工具失败、下一次 HTTP 失败或整题超时，前面记录的费用仍进入 `records.jsonl`；中止后没有新的请求或执行。

### 3. 接入统一 schema 和按批次扣点的工具执行器

输入为当前模式可用的工具及原参数定义；输出为唯一 `knowledge(operation, params)` schema、参数校验和批次执行结果。

| 检索模式 | 允许的 operation |
|---|---|
| bm25 | `rag_search` |
| grep | `grep_search` |
| both | `rag_search`、`grep_search` |
| facts | `lookup`、`query_operators` |
| hybrid | `rag_search`、`lookup`、`query_operators` |

schema 的 `required` 只要求 `operation`、`params` 字段存在，通过操作分支约束各自参数，并保留本地校验。统一函数不接受操作数组，不增加 `answer` 或 `finish`；一次 `knowledge` 调用恰好对应一次原检索操作。并行查询表现为多个独立的 `knowledge` 调用，各有自己的 call ID。

从 `agent.ts` 提取必要的工具分发门面，复用原检索器、facts store、来源标记、命中/注入统计及文本截断规则。调用参数无效时返回明确错误，不静默替换为原问题执行，也不查询未在当前模式开放的 operation。人工查询规则继续来自 `knowledge/AGENTS.md`，运行能力块从实际 schema 和配置生成。

响应已记录费用状态且通过截断检查后，一批调用才进入以下流程：

1. 检查调用 ID 可用于结果关联；缺失或批内重复 ID 视为协议失败，保存原响应和 usage，避免发出无法匹配的工具结果。
2. 按响应数组顺序同步预占剩余额度，全部预占结束后再执行。每个有名额的尝试扣 1 点，包括未知函数/操作、参数错误、空结果、执行失败及新响应中重复的查询；扣点后不退款。
3. 第五个获准尝试仍执行。无名额的调用不执行、不扣成负数，计入 `denied` 并返回 `budget_exhausted`。
4. 对获准且参数合法的独立操作并发派发，隔离单项可恢复错误；收齐本批后按原调用顺序回写结果。当前同步检索可复用，不为此增加线程池；同批多调用首先减少的是模型往返。
5. 每个可关联 call ID 都有一个结果，正常、空匹配、参数错误、执行错误及预算拒绝均覆盖。库完整性等系统故障直接中止单题，未完成项留在 trace，不伪装成无匹配或发送不完整批次续问。

例如剩 2 点时收到 A、B、C，A/B 先获准，C 被拒绝；即使 B 先完成，回写顺序仍为 A/B/C。HTTP 重试不扣工具积分，也不能使已完成的工具批次再次执行。

工具结果用简短结构包裹原证据：状态、是否实际执行、`data`、`budget_remaining` 和必要消息；同批统一使用预占完成后的余额。最后一批获准结果保留真实证据，并在余额为零时附“请依据已有证据作答，未覆盖部分明确说明”。超额调用返回 `status=budget_exhausted`、`executed=false`、余额 0 和同类作答提示，不能冒充证据。运行时结果与 trace 的 `writtenContent` 必须一致。

验收：剩 2 点时一批 3 个调用仅执行前两个；初始 5 点时一批 7 个只执行前五个；第 5 次保留证据，第 6 次起拒绝；错误和完成顺序不改变扣点或 call ID 关联。测试覆盖全部检索模式及当前模式禁用操作。

### 4. 替换主循环并收窄回馈兜底

输入为已具备预算和取消能力的批次执行器；输出为一份持续累积的 messages，以及模型自行结束的原生正文。

正常消息链为：

```text
system + 真实 user 问题
  → assistant.tool_calls[1..N]
  → 对应 tool 结果[1..N]
  → 后续 assistant.tool_calls 或最终 assistant.content
```

每次生成都提供同一模式的统一工具 schema，固定 `auto`。统一优先级为：保存响应与费用状态 → 检查截断及协议完整性 → 工具预占与执行或正文判定。`finish_reason=length` 等截断响应即使含合法的前缀调用也整批拒绝，记录未完成，预算不变、工具零执行，不继续请求；不能执行其中看似完整的调用。未截断且可关联的调用仅参数无效时，仍按第 3 步的错误尝试扣点规则处理。

通过前置检查后，有工具调用则处理完整批次；同一响应附带的正文是中间文字，不作为最终答案。工具返回后由模型决定下一批查询，允许五次有依赖的单工具查询跨越原三轮限制，再以第六次模型生成作答；独立操作可以同批提出。模型步骤数只作统计。

无工具调用且正文非空、未截断时，再检查回馈条件：

- 本题此前从未出现 `tool_calls`，回馈开启且尚未使用：保留该响应及成本到 trace，不将其作为最终答案；沿用现有丢弃正文的续传语义，不把该正文写回 messages。追加一次“请先调用本次可用的知识库工具查证，再依据结果作答”的程序化 user 回馈，记录 `origin=host_fallback` 和 `feedbackUsed=true`，随后仍用 `auto` 继续。
- 已触发回馈后仍无工具就作答：结束为 `no_tool_after_feedback` 未完成，保留正文供核查，不连续追加催询。该限制只约束异常回馈，不限制正常工具循环的批次。
- 本题已经提出过工具调用：直接接受合格正文。参数错误、无命中或预算拒绝通过 tool 结果处理，不转为 user 回馈；是否实际获得充分证据另由质量检查判断。
- 实验配置关闭回馈：允许直接接受合格正文，但在结果中标记未调用工具，避免与取证后作答混淆。

空正文且无调用、响应截断或协议结构无效走异常结果，不作为“未调用工具直接作答”触发回馈。人工查询规则补入唯一指令源 `knowledge/AGENTS.md`，包括先取证、独立事项可合批、依赖结果再续查、证据足够即可回答及预算耗尽后说明缺证；代码只负责检测条件、执行准入及生成对应状态反馈。

删除按 `maxRounds+1` 清空工具的路径，不加入正常阶段的 `required`、`none` 切换。余额为零后若模型继续调用，统一返回预算提示并继续 `auto`，直到模型输出最终正文或整题取消/超时。全程只存在一个真实用户问题，至多另有一次明确标注来源的宿主回馈。

验收：正常轨迹没有程序化 user 消息；直接作答的异常轨迹最多出现一次回馈；回馈不补充任务要求、不重置预算，也不覆盖用户问题。

### 5. 同步可观测性、报告和 dry 管线

输入为预算事件、模型步骤及结束状态；输出为能区分用户轮次、模型请求和工具执行的运行记录。

在 `trace.ts`、`types.ts`、`runner.ts` 和 `report.ts` 同步记录：模型生成步骤与 HTTP 尝试、含工具的批次数、调用提出/准入/实际执行/错误/拒绝次数、预算前后值、回馈次数、终止原因、每工具及整题结果字符数。统计明示口径：`used` 是准入尝试数，参数无效也占用；`executed` 仅统计实际调用底层检索实现的项。`toolRounds` 的展示改为“工具批次”，避免继续标成“检索次数”。

对模型保留外层函数名 `knowledge`，对报告和覆盖率保留解析后的原 operation，避免所有工具统计合并成一个名字。新增记录版本，旧 trace/费用记录保持可读；旧数据缺失的新指标显示不可用，不冒充零值，不重写历史运行产物。

`meta.json` 固定记录实际预算、固定 auto、并行参数、回馈开关、session 超时、schema 版本、查询指令哈希和原有模型/语料/检索参数。正常答案只来自最终 `assistant.content`；失败说明与未接受正文分开显示。继续使用现有敏感值遮蔽，不记录鉴权头或完整密钥配置。

dry 模式生成统一 schema 的调用，并覆盖至少一个同批多调用和一个依赖结果后再调用的轨迹，步骤计数不能再从 tool 消息数量直接推导。全部检索模式可干跑。

验收：同批三个调用显示为一个工具批次和三个尝试，费用只计一次模型响应；失败题的已知费用参与汇总，未查证答案和预算拒绝可单独定位。

### 6. 回归验证与成本、质量对照

先以确定性 mock 完成执行契约测试，再运行真实小样例及完整 20 题。复用 `agent.test.ts`、`provider.test.ts`、`facts-tools.test.ts`、`trace.test.ts`、`runner.test.ts`、`report.test.ts`，为批次准入和取消增加有行为意义的用例，替换依赖旧固定末轮的断言。

完整对照分为旧实现（原两点）、新实现两点、新实现五点。固定 Qwen3.7-Flash、关闭思考、温度 0、相同题集、语料、检索配置和输出长度；保留各自真实 schema、指令和代码快照。两点对照评估新循环、schema 与必要指令调整的组合效果，不将差异单独归因于某一项；新实现两点/五点用于观察扩大预算的效果。旧历史运行仅作参考，不能替代条件匹配的对照。

使用 [20 题答案核查基线](spec/rag-answer-baseline.md)逐题检查事实、证据覆盖和缺证说明。特别复核龙舌兰与但书：前期原型曾把每笔订单的交付数条件误读为连续成功/失败次数，功能链路成功不代表答案合格。对照中发现的新质量退步必须定位修复并复测；已有问题分别登记，不能修改游戏事实或暗中扩大工具额度来制造通过。

汇总每题及总输入/输出/缓存命中 token、已知费用、用量未知的请求数、完成率、回馈率、调用分布、拒绝后续调用数及 P50/P95 延迟。并行和提前结束有机会减少往返，五点上限也允许更多取证；不预设固定节省比例，不将 HTTP 请求数减少直接视为 token 等比例下降。真实基准原始结果放运行目录，实施笔记记录条件、结论和质量差异。

配套[实施笔记](plan-agent-auto-tool-budget-notes.md)已按模板建立，记录本次审查修订，后续编码时流式追加。代码检查执行 `pnpm run typecheck`、`pnpm run test`，构建后干跑；文档执行 `node scripts/doc-check.mjs`。合并前在实施验收完成并按文档生命周期归档后，执行唯一门禁 `node scripts/verify.mjs merge -- --base main`。当前计划的未完成清单会触发 D1，这是待实施状态，不提前勾选或绕过检查。
