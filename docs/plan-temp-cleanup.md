# 基准结果入库与分支收尾清理计划

> 创建日期：2026-09-05
> 更新日期：2026-09-06
> 状态：施工中
> 工作分支：`feature/temp-cleanup`

## 目标

基准结果提取进版本控制，团队能独立复核和比较；合并收尾后通过一份文本清单清理本机剩余产物。首版采用普通 JSON 文件与解析脚本，复用现有 bench CLI、tooling 和发布流程。

## 非目标

首版不做定时任务、按天保留、自动分支归属、工作树/rebase 映射、批次状态库或独立维护目录。清理脚本不管理合并、push、tag；不改变现有本机原始运行文件结构。

## 架构分析

2026-09-05 的历史盘点：dev-temp 共 657 个文件、16.40 MiB（其中 runs 为 242 个文件、0.21 MiB）；bench-runs 共 392 个文件、7.54 MiB，97 个运行目录中有 47 次 dry、48 次真实运行和 2 次未知分类。当时文件全部在近一周内，按周清理不适合当前紧凑节奏。本次不重新盘点。

已有 tmp clean 默认预览，但无龄期 apply 会清空 dev-temp 顶层，不能直接用于收尾。bench 已有 TypeScript 聚合器和 report/compare CLI，输入是调用级 CostRecord，包括 HTTP 尝试用量；共享快照必须保留这些事实，不能只存汇总。旧产物含备份且缺少分支归属，应显式选择，不能靠名称和时间猜测。

## 实施方案

实施顺序：先完成快照导出与解析，再接入报告和比较；随后实现清单生成、预览和删除，最后接入既有收尾流程并处理可恢复的旧证据。输入、输出和验收分别按下文约定。生产目录的真实删除必须等待证据共享条件满足，开发验证使用测试目录；不为验收发起真实 LLM 请求。

### 1. 文件结构：每次运行一个 JSON

| 文件 | 职责 | 入库 |
| --- | --- | --- |
| `bench/results/<run-id>.json` | 一次运行的完整共享快照 | 是 |
| `dev-temp/cleanup-<名称>.json` | 一次收尾的显式路径清单，旧存量也使用同一格式 | 否 |

只新增 bench/results 这个共享目录；实验主题是 JSON 字段，不再增加主题子目录、逐次运行子目录或中央索引。不固定生成 manifest、summary、queries、report、评价等多个文件，也不维护跨文件哈希清单。

选择 JSON 作为唯一机器输入：原生解析器即可处理类型、null、多行答案及校验，避免另造 Markdown 表格或代码块解析约定。Markdown 用现有报告渲染器按需输出；人工结论继续写对应 plan/notes/spec，引用快照路径，不为每次运行新建评价文件。首版不同时支持 JSON/Markdown 两套输入格式。

### 2. 快照只保存原始事实，汇总按需计算

单个快照的顶层结构限定为 `schemaVersion`、`runId`、`topic`、`meta`、`queries`、`records`：

- meta：运行时间、非敏感模型/检索/预算等参数、价格快照、运行时源码版本及 dirty 状态、题集/语料/指令来源信息。
- queries：完整输入题集及每题最终答案、状态、终止原因、预算/轮数、必要命中与注入 ID。没有 CostRecord 的失败题也必须保留。
- records：白名单提取现有 CostRecord，保留 aggregate 所需全部计量字段，包括 HTTP attempts 的用量、计量口径和重试事实。排除无关响应正文及敏感诊断文本，不复制完整 trace。

不持久化第二份总体/逐题汇总；report/compare 从 records 调用现有 aggregate，并结合 queries 补齐失败题和真实题目分母。未知用量保留 null、不完整费用保留已知小计，不能补为零或完整。请求完成不等于答案正确，人工评价仍明确写出依据。

新增导出模块放在 bench/src，通过现有构建后的 bench CLI 暴露 export；快照解析/校验与导出先放同一模块，不预拆 schema、registry、repository、adapter 等文件。report/compare 增加快照输入，保留原始运行目录输入。tooling 不新建 bench/export task，不复制 TypeScript 聚合逻辑，也不引入第二个构建入口。

现有 `bench validate` 入口同时枚举 `bench/results/*.json` 并复用快照读取校验；共享快照缺失或任一文件不符合同一 schema 时，完整性校验失败。

新运行在现有 meta 中补充必要来源字段即可，不增加旁车状态文件。正式基线优先使用已提交代码；dirty 或历史版本信息缺失如实标注，不能用导出时 HEAD 回填。完整题目保存在 queries；语料与代码引用可取得的 Git 版本，无法取得的来源注明限制，不因缺失信息自动付费重跑或搭建通用源码打包系统。

导出字段白名单并脱敏，包含对答案、问题、错误文本中敏感值的检查。相同 run-id 与相同内容重复导出幂等，内容冲突拒绝覆盖。真实基准默认保留失败对照；只有明确不作证据的探针才可登记舍弃理由。支撑正式结论的结果必须入库，不能只选择表现好的运行。

### 3. 清理只解析一份显式清单

清单用一个 JSON：`schemaVersion` 和 `entries`。每个条目记录仓库相对 `path`、预览时脚本计算的 `fingerprint`，以及 `snapshot`（对应入库快照路径）或 `reason`（无须保留/明确舍弃理由）。不记录分支状态、工作树标识、发布阶段或远端状态。

扫描只提供候选；由本次收尾明确选择可以删除的路径，脚本据此生成清单与指纹。指纹覆盖候选内容与结构，生成和执行前使用同一算法；清单自身不得成为删除目标。选择路径不代表脚本自动认定分支归属，未知产物、备份及其他分支实验不加入清单。main 验证日志也按具体路径选择，不建立归属协议。

清理入口为 `node scripts/tooling.mjs tmp clean --manifest <清单> [--apply]`。默认只预览，列出文件数、体积、提取去向/舍弃理由和跳过原因；apply 按清单复核后删除。旧全清入口不接入收尾流程。

清理器只检查本地事实：候选仍匹配指纹；snapshot 存在且其内容已提交、工作区无改动。快照数据正确性由 bench 校验器和合并门禁负责，清理器不实现第二份基准 schema 或费用计算。是否完成合并和共享由既有发布流程负责，不通过 --merged 参数、远端查询或发布状态文件重复判断。

清单成功后移除；部分失败保留原清单，已删除条目重试时显示已不存在，剩余条目重新复核。结果输出终端，不增加永久清理日志或状态数据库；需要调查时由操作者保存输出即可。

### 4. 最小删除保护

- 固定白名单为 dev-temp 内明确选中的产物与 bench-runs 下运行目录；拒绝根目录本身、越界、符号链接/junction 等不支持的重解析点。脚本中的真实路径检查在扫描和删除前执行。
- Git 跟踪文件、候选或祖先/后代的 `.keep` 均保护；拒绝重叠候选，避免重复递归删除。
- 清理是停止相关实验后的收尾操作。运行中或无法确认停止的目标不进入清单；标准运行复用现有结束产物判断，旧脚本由操作者核对，不为所有生产者新增终态/租约协议。不能把“暂时没写文件”当作运行结束证明。
- 删除前重查指纹与保护条件，变化即跳过。文件占用、权限错误和部分失败如实报告，不静默宣称成功。首版不支持清理与同一目标写入并行执行。

scripts/scratch 不扩入首版自动删除白名单；有用脚本按现有 promote 流程处理。确需删除的遗留 scratch 另行显式操作，不因为名字含临时就扫描全仓。

### 5. 接入既有收尾流程

1. 合并前导出基准单文件快照，结论引用快照；走现有提交流程，不由导出器自动暂存/提交。共享快照校验在干净克隆也可执行，不依赖忽略目录。
2. 按原流程执行合并门禁、合并、发布验证及推送。门禁/推送失败保留原件；快照进入共享提交后，才进入证据原件清理步骤。
3. 停止相关实验，选择本次可删除产物，生成清单并预览，然后执行 apply。更新 release-workflow 的收尾步骤与 scripts/INDEX 的用法；不新增 hook 或发布编排脚本。

开发期间保留当前实验与失败现场；合并共享后立即清理已提取原件、dry 与无须保留的中间产物，不再额外等待天数或保留最近 N 次。清理失败不撤销合并，可独立重试；普通可重建产物手动清理不必继承基准证据的共享前置条件。

旧存量复用同一流程与同一清单格式：真实运行及 dev-temp 中散落实验提取可恢复快照，未知来源如实标注；备份/未知文件保留。先固化被文档引用的结论并更新路径，再在共享完成后清理，不另建迁移系统。

## 验收清单

- [x] 每次基准只新增一个共享 JSON，无固定汇总/报告/评价旁车文件。
- [x] 无原始 bench-runs 的干净克隆可重新生成报告、比较结果、复核答案；失败题、HTTP 重试计量和未知用量正确保留。
- [x] 导出、解析、校验在 bench 内复用现有类型与聚合；同内容幂等、冲突拒绝覆盖，脱敏与来源缺失处理正确。
- [x] 日常收尾和旧存量使用同一清单格式；不引入批次/工作树状态库、自动归属或远端发布判断。
- [x] 默认预览不改产物；验证路径/junction、跟踪文件、`.keep`、重叠候选、指纹变化、未提交快照与部分失败重试。
- [x] 未确认停止的目标跳过；既有收尾流程在合并验证和共享失败时保留证据原件。
- [x] 文档路径引用更新，必要证据入库；typecheck、test、doc-check 通过，合并走统一门禁。

## 关联 ADR

本计划不引入跨模块归属协议或新依赖，复用现有接口与模块边界，暂不新增 ADR。实施中若触及仓库 ADR 触发条件，再补充对应决策。实施笔记见 [plan-temp-cleanup-notes.md](plan-temp-cleanup-notes.md)。
