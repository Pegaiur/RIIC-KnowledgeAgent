## 决策偏离
> spec 中没有提到，但在实施中做出的重要决策

### 2026-09-01 — golden 键采用「清洗标题键 + 双层解析」而非字面 chunk.id
- **背景**：草案写 golden 键 = `file#heading`（"即 splitChunks 生成的 chunk.id，heading 为清洗后标题"）。实测发现 chunk.id 实为 `file#` + **原始标题行**（含 `## `/`### ` 前缀，如 `0-规则/发电站机制.md### 无人机机制`），与草案描述不符。
- **选项**：
  - A: gold.json 全部用字面 chunk.id（含前缀与空格）
  - B: gold.json 用清洗标题键，loadGold 双层解析（① 精确 chunk.id → ② `file#清洗标题` 回退），`--check-gold` 兜底校验
- **决策**：B。清洗键可读易维护；不改 267 个 chunk.id（避免牵动 agent 溯源标注格式与历史 runs 可比性）。
- **影响**：`hitrate.ts` 的 `resolveGold` 承担解析与校验；同名清洗标题歧义（如莱茵科技.md 两个「机制」）依赖精确 id 兜底，当前 gold 未引用歧义键。

### 2026-09-01 — gold 转录的映射决策（出处串 → 实际小节）
- **背景**：基线出处为 `file#小节1/小节2/…` 汇总串，部分小节名与语料实际标题不一致；S01 含通配 `2-体系/*`、F09/S04/S05/S08 含文件级出处（无小节）。
- **决策**（逐项对照 chunk 清单后映射）：
  - 不一致小节名：F04「固定双人combo」→ `固定双人 combo`；F05/F09「核心干员」→ `公招刷新取向`；F05「斥罪vs凯尔希」→ `斥罪 vs 凯尔希·思衡托`；F06「派系计数型」→ `派系计数型（核心体系依赖）`；F08「中枢和宿舍轮换规则」→ `宿舍：不轮换` + `中枢：随体系同上同下`；F08「为什么长班12小时短班6小时」→ `为什么长班 12 小时、短班 6 小时`；F10「裁缝技能的效果是叠加的」→ `裁缝技能的效果是叠加的，不是覆盖的`；S03「构成」→ `架构` + `成员`，「与其他体系关系」→ `兼容`（深海链.md 无该节名）；S06「成套组成」→ `核心双人（缺一不可）` + `感知生产者（越多越好）`，「数值锚点」→ `迷迭香制造效率` + `黑键贸易效率`；S07「与其他体系的关系」→ `中枢共存` + `明确不选清单`（与草案预判一致，展开后恰为 10 项）
  - S01 通配 `2-体系/*`：按 S01 参考要点落点收敛为 体系总览 3 节（243 示例 / meta_chain 互斥组 / 其他互斥）+ 发电站虚拟电站 + 五体系文档核心节（但书链成套组成 / 巫恋核成套组成 / 迷迭香核心双人 / 自动化组成套组成 / 红松林中枢）
  - 文件级出处按要点落点收敛：F09 办公室机制.md → 公招刷新取向 + 斥罪 vs 凯尔希·思衡托；S04 贸易站机制.md → 赤金订单分布、buff叠加模型.md → 归零与裁缝两节；S05 发电站机制.md → 虚拟电站、制造站机制.md → 设施数量依赖型；S08 控制中枢机制.md → 派系计数型
- **影响**：gold.json 20 题 / 121 项，`--check-gold` 首跑全通过；映射判断留痕于本节，后续复测可直接复用。

## 实现调整
> spec 中有描述，但实际实现方式不同

### 2026-09-01 — runHitrate 单次检索派生多 K，miss 记录视野内最佳位次
- **spec 原文**：`runHitrate(index, chunks, questions, topKs)`——输出 recall@3/5/10 曲线 + 逐题明细 + miss 题最佳位次。
- **实际做法**：每题只检索一次（视野 = max(topKs, 20)），从同一排序派生各 K 命中与位次；视野内未进任何 topK 的 golden 记 `第 N 位`，视野外记 null。签名增加 gold 参数（草案漏写数据来源）。
- **原因**：避免每 K 重复检索；最佳位次需要比 topK 更深的视野信息。
- **后果**：无（口径与草案一致，多 golden 按比例计）。

## 意外发现
> 实施中发现的 spec 未覆盖的依赖/边界/风险

### 2026-09-01 — recall 远低于 90% 判据，但失败模式异质，jieba 并非普遍对症
- **发现**：recall@5 = 33.5% ≪ 90%，R3 按草案形式触发。但 spot-check（G01/S03/F06 三例）显示三类失败模式：
  - **a. 泛化标题碰撞**：「缺人降级路径」「数值锚点」等节名遍布所有体系文档，单 query 词面匹配被跨文档稀释（S03 top-10 中 6 席是其他体系的「缺人降级路径」）。**jieba 不改变词面重叠，对此无效**。
  - **b. 实体词表缺失**：G01 查询无干员名，目标「散件干员速查#贸易站」表格块排第 20 位——对症方向是 terms.ts 词典 + P2 专名 boost（草案 R3 前置小步已含 terms.ts 抽取）。
  - **c. 多节 golden 口径严格性**：S 类题 golden 7-11 节，单轮 topK 无法全覆盖。agent 实际是**多轮累积注入**（2 轮 × topK5 + 引导改述），与单轮 recall 低不矛盾——P1 实测 14 正确 / 仅 1 编造即为佐证。
- **影响**：R3 触发成立但预期收益集中在 b 类（词典覆盖）；a 类需要 query 改述/多轮检索兜底（agent 已部分做到），c 类需要按草案 R1 的「注入覆盖率」口径判定。**下一步优先级建议：terms.ts 抽取（三处共用词表）→ R3 jieba 复测（同口径对照）→ R1 矩阵（注入覆盖率口径）**。
- **交叉验证**：G01 在历次 agent 运行中反复漏检/编造（基线 / P1 / R1-B / P5 均命中陷阱点），与 recall@10=0、第 20 位完全吻合——hitrate 工具与 agent 行为互证有效。

## 债务记录
> 遗留的技术债、被牺牲的改进与延期偿还事项

### 2026-09-01 — hitrate 为单轮单 query 口径，未模拟 agent 多轮累积注入
- **债务**：单轮 recall@K 与 agent 实际检索行为（minRag 引导 + 2 轮 + 改述）存在口径差，直接用 recall@5 判「检索器好坏」会高估差距。
- **未来偿还**：R1 判定按草案改用「注入覆盖率」（|golden ∩ 实际注入片段|，对各组 topK 分别计算）；若需要更贴近真实的检索器对比，再扩展 hitrate 多轮模式。

### 2026-09-01 — hitrate 结果无入库快照
- **债务**：运行明细仅输出控制台 + `--out`（dev-temp 不入库），跨日复测对比需靠本笔记关键表。
- **未来偿还**：若 R3 复测需要严格逐题对比，考虑让 hitrate 结果写入 `bench/runs/<ts>-hitrate/`（复用 runs 目录约定）。

## R3：jieba 中文分词复测（2026-09-01）

> 对应草案：docs/draft-retrieval-tuning.md「R3 中文分词 jieba」；ADR：docs/adr/ADR-001-jieba-node-中文分词.md。
> 前置：terms.ts 词表抽取完成（grep-retriever 迁移 + jieba 词典 + 后续 P2 共用）；`BENCH_TOKENIZER=bigram|jieba` 参数化，默认 bigram 不变，meta.json 增 tokenizer 字段。

### 决策偏离
- **initTokenizer 落在 retriever.ts 而非 terms.ts**：草案建议「terms.ts 暴露 initTokenizer()」，但 terms.ts 定位为纯数据（词表），initTokenizer 依赖 jieba-node——放 terms.ts 会让 grep-retriever 传递性引入 jieba。实际：terms.ts 纯数据，retriever.ts 持有 initTokenizer（幂等：setLogLevel SILENT + ENTITY_WORDS 逐词 addWord；addWord 触发词典惰性加载）。
- **jieba-node 实测口径修订**：ADR 调研结论「纯 JS」经安装核实成立（package.json 自述 Pure JavaScript，无原生构建脚本）；`addWord` 无需显式 initialize 即触发词典加载（~0.23s）；INFO 日志需 setLogLevel('SILENT') 静默，否则污染 CLI 输出。

### 复测数据（同口径：20 题 / 121 golden / 267 chunks / 含 L1 锚点）

| topK | bigram（基线） | jieba | 差值 |
|---|---|---|---|
| 3 | 21.3% | 19.2% | −2.1pp |
| 5 | **33.5%** | 29.4% | −4.1pp |
| 10 | **50.3%** | 41.9% | −8.4pp |

逐题（@5）关键变化：S04 4/9→1/9、S06 1/11→0/11、S02@10 3/9→1/9 显著退化；仅 F06 0/5→1/5、F07 2/5→3/5、F10 2/7→3/7 零星改善；G01 两版均为 0（第 20 位 → 视野外）。

### 归因（S04 spot-check）

- **bigram 的字符级部分匹配是隐性容错**：查询措辞 ≠ 语料措辞时（S04 问「如何运作/提升效率」，语料小节为「效率分档/缺人降级」），bigram 凭 裁缝/效率/运作 等双字碎片仍能累积部分证据；jieba 词级精确匹配后，这类模糊重叠大幅减少。
- **疑问词成为高区分度词元反噬排序**：「为什么」在 jieba 下是低频高 IDF 词元，而 buff叠加模型.md 有 4 个「为什么……」标题小节——S04 top-8 被其占 3 席，体系文档自身小节（一句话结论/成套组成/效率分档）反而挤出前排。bigram 下「为什么」碎片化为 为什/什么，区分度被稀释，无此效应。
- **与 R2 失败模式预判吻合**：R2 已判「jieba 对 a 类（泛化标题碰撞）无效、c 类（多节 golden）无效」；实测它还损害了原本依赖 bigram 模糊性的部分 b 类场景。MTEB 0.359→0.641 的先验来自查询与语料措辞高度一致的法律语料，本语料库不满足该前提。

### 结论 / 判定

- **jieba 复测无提升、全面略降 → 默认保持 bigram**（本就是默认值，无需回退动作）；依赖与参数化代码保留（ADR-001 后果条款：触发条件未消失，未来可作混合分词 / 词典调优的实验基座）。
- ADR-001 状态更新为**已实施**，后果记录复测结论。
- **R2/R3 联合指向**：检索器词元层的可改进空间已被压缩（bigram vs jieba 两端都不高），瓶颈回到 c 类（多节覆盖需多轮累积注入）与 b 类（实体词典命中，未测试 P2 专名 boost）——下一步按草案转 **R1 注入收敛矩阵（注入覆盖率口径）**，或先补 P2 专名 boost 实验。

### 债务记录
- jieba 与 bigram 的**混合分词**（token 并集）未实验——可能是兼顾词级精确与字符级容错的方向，另行评估。
- ENTITY_WORDS 词表未经系统化全量校对（如 灰毫/远牙/野鬃 等体系干员缺失），P2 专名 boost 前需补全。
