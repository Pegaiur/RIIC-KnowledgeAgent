# Agent 高 ROI 调优评估草案

> 创建日期：2026-09-05
> 状态：提案中

## 目标与判断

优先改善错误答案和无效调用，以预期收益、改动复杂度及验证成本判断 ROI。先调整现有控制流和工具/回答契约，再决定是否调整检索与模型；本草案记录评估结论，核心调优尚未实施。方案 1 已转为 [请求阶段工具约束计划](plan-agent-tool-request-policy.md)，方案 2、3 继续留在本草案。显式温度对照已完成六轮真实运行，未发现足以切换默认值的质量收益。

前置 trace 缺陷已修复于 `2b85348`；本次复验 facts 工具正式测试 39 项、独立验收 15 项均通过。

| 项目 | A | B |
|------|---|---|
| 完成题数 / LLM 调用数 | 20 / 49 | 20 / 47 |
| 工具请求 / 实际执行 / 预算拒绝 | 32 / 29 / 3 | 29 / 27 / 2 |
| lookup 空结果 / lookup 请求 | 4 / 7 | 3 / 4 |
| 被最少检索约束丢弃的回答 | 1 次，715 输出 token | 2 次，2,226 输出 token |
| RAG 单次写回平均 / 最大字符数 | 1,273 / 2,590 | 1,432 / 4,679 |
| 最终答案输出 / 全部输出 token | 14,059 / 15,876 | 14,816 / 18,044 |
| 成本记录求和 / 整批耗时 | ¥0.026656 / 180.7 秒 | ¥0.027820 / 200.0 秒 |

两轮都将“怪物猎人小队”“深海猎人”“格拉斯哥帮”交给 lookup 并得到空结果；本地按相同字符串调用 `query_operators({ faction })`，分别能命中 3、5、4 张卡。A 的另一次空 lookup 为“红松林骑士组”，直接改用同名 faction 也为空，不能把所有组合名机械改成阵营过滤。

F05、S08 两轮均完整注入 gold，但答案仍追加缺乏本次证据支持的结算关系或对象解释。B 的 F02 所需机制块仍未命中，答案却补写基础生产时间、心情规则等具体数值。当前同时存在工具选错、关键证据漏召回，以及证据不足或已有证据时继续外推的问题。

## 优先方案

| 顺序 | 方案与最小改动 | 收益依据 | 成本与判断 |
|------|----------------|----------|------------|
| 1 | **把已有工具约束落实到请求阶段**：预算耗尽后提供空工具集；Qwen off 路径在尚未满足最少检索且仍有预算时试用 `tool_choice: required`，满足后恢复 auto，末轮作答优先 | 两轮共有 4 个 LLM 轮次只产生被预算拒绝的请求，另有 3 次提前回答被丢弃，共 2,941 输出 token | 改动小，控制流收益证据最明确；上述次数是历史可优化机会，不是未来节省保证 |
| 2 | **明确 facts 查询对象**：lookup 描述区分干员/技能/技能等价组与阵营/组合；阵营成员交给 query_operators，组合机制交给 rag_search；空 lookup 返回简短的下一步查询提示 | 同样三种阵营名在两轮都选错工具；S03 两轮均在错误 lookup 后耗尽预算，正确的 faction 查询被拒绝 | 改动小，有重复失败和可用替代路径；先改工具描述和提示，不增加通用分类器或自动回退链 |
| 3 | **缩小回答展开范围，并让关键结论带简短出处**：按用户子问题回答，保留必要练度/设施/触发条件；对象、数值、技能名来自对应工具文本，缺证据直接说明；去掉题目未要求且证据未提供的外文别名、额外案例和结算推测 | 最终答案占两轮输出约 89% / 82%；F05/S08 证明增加召回不能单独解决外推 | 修改现有 knowledge/AGENTS.md 的回答约定即可；预期质量收益高但需实测，不能仅因回答变短或带引用就认定改善 |

第一项按独立计划分成“额度耗尽撤工具”和“Qwen off 强制最少查询”两步，各自验证。仍保留执行侧预算检查，以处理同轮多工具请求超过剩余额度的情况。A 的 G02 属于这种情况，不能算作在下一轮撤掉工具就能消除的往返。

[百炼 Function Calling 文档](https://help.aliyun.com/zh/model-studio/qwen-function-calling)说明可用 required 强制至少一次工具调用，并限制思考模式下使用该策略。实施时先对当前 Qwen3.7-Flash 非思考端点做小样例验证，限定生效范围；Hy3 与思考模式沿用原策略。此项不改变“至少检索一次”的业务要求，只将约束提前到请求阶段。

## 已完成的温度实验

**显式温度对照：0.2 与 0.7 各三轮，其他显式配置保持基线。** provider 已支持传入 temperature，meta 与目录名记录设置；默认仍不发送该字段。[百炼 Chat Completions 文档](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions)列出的 Qwen3.7 非思考默认值为 0.7，但最初两轮 A/B 没有快照服务端温度，不能据此追认其确切值。

| 六轮实验指标 | 0.2 | 0.7 |
|------|------|------|
| 每轮平均成本 / LLM 调用 | ¥0.029086 / 48.0 | ¥0.028843 / 47.3 |
| 共同 19 题的 RAG gold 覆盖 | 110/192（57.29%） | 108/192（56.25%） |
| 空 lookup / 工具预算拒绝 | 7 / 5 | 6 / 7 |
| 被最少检索约束丢弃的回答 | 6 次，7,523 输出 token | 6 次，5,670 输出 token |
| 截断 / 最长回答字符数 | 0 / 2,358 | 1 / 8,807 |

六轮均完成 20/20 题，完成仅指运行无异常。共同题集排除 S02：0.7 第三轮该题仅用 facts，无法按 RAG chunk 覆盖与其余运行直接比较。原来仅统计实际使用 RAG 题目的每轮覆盖均值为 56.04% vs 55.54%；所有覆盖口径都不等同于答案正确率。

F02 六轮中仅一次注入所需机制块，该次也明确回答 `1 + X + Y`；其余五次没有注入该块。S05 六轮均只有 1/5 个 gold 键覆盖，并持续出现设施分工错误。工具选错、证据漏召回和证据外推未被降温解决，继续维持上面的三个优先方案。

0.7 第二轮 S08 出现外文别名自我纠错循环并达到 4,096 token 上限；这只是“0.2 可能更稳定”的候选信号。本轮样本每组仅三次，且先跑完 0.2 再跑 0.7，未做完整答案盲评；不认定质量等效或稳定性优势。后续如专门比较稳定性，应保留两组并交错扩样。不要通过直接压低 max_tokens 来代替回答范围约束，以免只截断答案而遗漏条件。

温度实验汇总及独立复核分别位于 `dev-temp/temperature-comparison-2026-09-05.md`、`dev-temp/temperature-audit/report.md`；本次重放 163 次本地工具调用均与产物一致，typecheck、build 和 198 项正式测试通过，未增加真实模型请求。

## 当前不优先的方案

对两轮实际 RAG 查询词做了本地检索对照，查询词固定、沿用原来的 12,000 字符注入规则；未调用 LLM 重新生成答案。

| 候选 | 离线结果 | 判断 |
|------|----------|------|
| topK 5 → 8 | B：gold 键覆盖 39/69 → 43/69，工具写回字符 32,931 → 62,935；A：38/64 → 43/64，28,013 → 51,378 字符 | 覆盖有增益，但文本接近翻倍；先处理错工具和外推，再试是否值得 |
| 增加 maxContextChars | 两轮单次 RAG 写回均低于 12,000 字符上限 | 当前没有解决的瓶颈 |
| 固定五个槽位中优先保留 1–2 个 base/guides 块 | 两轮总 gold 覆盖均未增加；保留两个槽位时，S07/S08 都有关键块被挤掉 | 不采用固定配额；不能把“优先散文”当作通用修复 |
| 全局增加工具次数或轮数 | 当前空 lookup 已消耗预算，且许多题只检索一次便作答 | 先消除错误调用；增加上限是否有益，需观察修复后的轨迹 |
| 新增向量库、reranker、第二个审查模型或通用规划器 | 现有证据尚不能证明需要这些机制 | 引入与验证成本更高，留待低成本项验证后重新判断 |

A 的 RAG 覆盖仅统计实际使用 RAG 的 19 题、64 个 gold 键；S02 仅使用 facts，未把卡片强行映射成 chunk。B 的 20 题都使用了 RAG。两组覆盖不是答案通过率，不能直接比较两轮质量或将 topK 的离线增益当作实际回答提升。

检索仍有后续工作：例如 F02 所需机制块在两轮实际查询中均排到全库第 27 位，topK=8/10 都没有解决；这类问题应单独研究设施机制词与排序，不靠无差别增加上下文。

## 最小验证顺序

1. 控制流先用固定 mock 检查最少检索、预算耗尽、同轮多调用和末轮作答，再确认 Qwen off 的 required 支持。
2. 用 F02、F05、F10、S02、S03、S05、S08、G02 做诊断小集；固定 hybrid/off、显式温度对照值与原检索参数，分别验证 facts 查询契约和回答约束，避免一次叠加后无法归因。温度实验已完成，本轮不据此切换默认值。
3. 以现有 spec 的必须覆盖项、明确错误和无依据补写为主要人工判据，同时记录空 lookup、拒绝轮次、被丢弃回答、token 与耗时。不能靠大量回答“未知”来换取表面上的少错。
4. 对有收益的候选重复确认，再跑完整 20 题检查其他题是否退步；必要时加入不含题号特判的同类改写问题。成本按正确答案的收益判断，不只追求总费用下降。

详细离线结果与脚本位于 `dev-temp/agent-tuning-evaluation/`；真实证据仍由对应 `bench-runs/` 产物保存。方案 1 的实施与验收以独立计划为准，其余方向确定后再转 plan；如引入跨模块公共接口变更或新依赖，按仓库规则补 ADR。
