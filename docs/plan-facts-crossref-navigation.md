# facts 组合跨引用导航备注补充计划

> 创建日期：2026-09-11
> 状态：施工中

## 目标

为「干员名、组合相关阵营词或技能组词命中后，返回卡缺少组合协作导航」这一类问题，在 curation 层补充干员级备注（operator notes）：使核心成员、增强成员或开放技能组的线索随已返回的卡一并出现。三类线索分别说明，不把增强成员写成启动必需。

主要工作是逐条核实并补备注；不改检索、分块、匹配逻辑，也不改变当前唯一 facts 查询工具 `facts_search` 的命中集合。

## 非目标

- 不改检索、打分、分块与 facts 匹配逻辑（小节命中是另一条线，另行评估）。
- 不改题集、gold、spec、知识库 references 与 guides。
- 不处理「combo 登记名与阵营名差一字」的入口词条问题（单独决策）。
- 不补零命中的入口词条；零命中与其他入口上的导航缺口可以同时存在，不能据此排除整个组合。
- 不针对 benchmark 题号、问法或预期答案做特判；不新增按题目分支的逻辑。
- 不新增哈希/指纹字段：operator notes 不引入 expectedHash（遵循 AGENTS.md 编码核心约束 #10），漂移风险用指向式与来源标注降低。
- 不删除或改造内部遗留的 `lookup` / `queryOperators`（它们不在工具面内，仅供历史回归与旧数据调用者使用）。

## 架构分析

**facts 工具面现状**：hybrid 模式实际只下发 `rag_search`、`facts_search`、`read_section`（bench/src/tool-executor.ts 的 `allowedOperations` / `toolsForRetriever`）。`facts_search` 是唯一 facts 查询工具（bench/src/types.ts 的 `isFactTool` 仅认 `facts_search`）。`lookup` / `query_operators` 已是历史名：不在 `CurrentToolId` 内，被提交时走 `unknown_operation` 且不执行，仅保留在 `ToolId` 联合类型与 `isHistoricalFactTool` 中用于读取历史记录和报告聚合。`CardStore.queryOperators` / `lookup` 仍作为内部方法存在，但 bench/src 内没有生产调用者，只有测试调用。

**notes 机制**（bench/src/facts/store.ts、bench/src/facts/project.ts、bench/src/facts/curation/types.ts）：

- `buildTermIndexes` 只登记 canonical／技能名／技能组／设施／阵营／职业，`card.notes` 与 `skill.notes` **不进入 `facts_search` 索引**。
- 但 `serializeCard` 会把 `备注：…` 渲染在**任何被返回的卡**上。
- operator notes 全局按键 `operatorId` 唯一，重复登记直接抛错；批次 `room` 对 skills/grants 校验设施一致性，对 operators **不校验**（属人工约定）。

因此 notes 的定位是**导航**：不改变 `facts_search` 命中集合，只让已被返回的卡携带跨引用线索。

**现状统计**（独立复核成立）：全库 **425** 张记录卡，卡级 notes 仅 **2** 张（巫恋、孑，均在 trade.ts），技能级 notes **0** 条——notes 通道几乎未被使用。`control.ts` 与 `manufacturing.ts` 目前为空批次。

**实证样本**：本轮 GLM low 单轮 20 题核查的 S07.2。

- `facts_search("红松骑士团")` 命中 5 张卡（焰尾、远牙、灰毫、野鬃、正义骑士号），**5 张卡的 notes 全为空**，输出里没有指向薇薇安娜的任何信息；该次查询未送达她的技能证据，回答遗漏「薇薇安娜精二按每名制造站骑士干员 +7%」。这支持导航缺口判断，不证明补备注后模型必然跟进或答对。
- 其中**正义骑士号仅因阵营同为红松骑士团而返回，并非红松骑士团组的搭配成员**——这类「检索返回但非成员」的对象不得进入补备注名单。
- 同一组合换词可命中：`facts_search("红松骑士团组")` 走 combo 路径，返回 6 张卡，**含薇薇安娜**的「烛骑士微光」。
- 数据并未缺失；缺的是「已返回卡上的指针」。

判定口径见 docs/spec/rag-answer-baseline.md 的「使用口径」（证据块可由等价记录替代；未检索到不等于不存在）。

## 判定口径

审计单位为「组合＋具体入口词＋导航目标」，干员正式名与阵营、技能组词采用同一口径。成员身份以 guides 组合文档、bench/src/facts/curation/terms.ts 的成员表及 coverage/openScope 为依据；开放组合未逐名列出的可适配成员不能直接认定为非成员。

- **核心成员导航缺口**：入口命中至少一张可承载导航的成员卡，但未返回目标核心成员，且返回文本没有指向目标的等价线索。组合名能查全不撤销其他入口上的缺口。
- **增强成员导航缺口**：缺少有来源依据的重要或可选协作成员线索；可以补充导航，但不能仅凭 important 标签断言其无可替代或为启动必需。
- **开放技能组导航**：成员可按技能条件替换时，优先指向可检索的技能组词，并注明组合所需人数、是否包含核心及解锁条件，不枚举固定搭配名单。
- **零命中入口**：记录为词条覆盖现象，补词条仍属非目标；同时核对该组合的其他已列入口，不将整个组合归为「只有词条覆盖缺口」。
- **当前入口无需补充**：仅对已核查且成员或等价导航线索充分的具体入口成立。未枚举所有入口时，不写整个组合「不需要」。

## 候选清单（已核实入口与补充方向）

前轮曾扫描 19 个 combo 并进行子代理校核。2026-09-11 的后续源码查询复核确认原 10 条缺失现象，但发现原「10 组需补／6 组不需要／3 组待核」分类不一致。已采纳以下三处修正：零命中不能排除其他入口的导航缺口；撤回组合级「不需要」的过度结论；开放标准化成员不按显式名单排除。历史扫描完成不代表修订后的全部入口已穷尽或备注已实施。

### 水月标准化组：改为技能组导航并注明人数

- **落位与入口**：在水月的 operator notes 中补充；`facts_search("水月")` 返回水月卡时携带技能组导航，`facts_search("标准化类技能")` 返回水月卡时也可见同一备注（水月持有「标准化·β」，属该技能组）。
- **拟用文案**：「水月标准化组以水月精二为核心；同一制造站另配两名已解锁标准化类技能的干员，与水月共三人。可用 facts_search 搜索『标准化类技能』选择适配成员，按各自技能解锁条件核对。」
- **人数语义**：这里的「两名」是水月以外的同站搭配人数，不是全库可选人数；水月包含在三人总数内。它是 guides 的组合配置条件，不改写为水月技能必须凑齐三人才生效。
- **开放成员**：历阵锐枪芬、洋灰、流星、石英、褐果、夜刀持有标准化技能，属于可按解锁条件适配的开放成员，不再列为「非成员排除项」。本方向通过水月卡引导技能组查询，不为这些成员逐张复制固定名单。
- **涤火杰西卡边界**：`标准化类技能` 不返回她的现象成立，但她属于中枢增强成员，不计入上述制造站三人，也不是启动必需。本次水月补充采用技能组导航，不以缺少她为「核心证据缺口」。
- **来源**：knowledge/guides/制造站组合.md「水月标准化组」；knowledge/references/技能-制造站.md「水月 ☆6 · 特种」及适配成员小节；bench/src/facts/curation/terms.ts「水月标准化组」的开放范围。

### 其余组合与入口边界

其余 3 组为企鹅物流、赤金工艺组、红云组，当前不预设备注补丁：`企鹅物流`、`金属工艺类技能`、`红云组` 的指定入口可返回已登记成员；德克萨斯卡还已点名拉普兰德、能天使。这些事实仅支持具体入口的覆盖，不能证明所有成员名或机制词都没有缺口。按统一入口口径补完审计后再决定是否补充，尤其红云组要按「两条重要分支任选其一」判断，不把所有 important 成员都写成必需。

成员排除须针对具体组合并核对开放范围。正义骑士号不作为红松组合成员、新约能天使不作为能天使组成员、星熊不作为龙门中枢组成员等结论保留；不能只凭阵营、设施不同或未出现在显式成员表中排除对象。莱茵生命阵营与莱茵科技技能成员不等同，约束的是成员身份，不能单独用作取消导航缺口的理由。

## 备注书写规范

- **落位（已确认）**：先用现有 operator notes 机制，写在**会被返回的成员卡**上，按该成员技能所属设施的 curation 批次归位（焰尾→control.ts、多萝西→manufacturing.ts、陈／诗怀雅→control.ts 等）。该归位是人工约定，`validateCurations` 对 operator 批次不做设施一致性校验。
- **现状**：control.ts 与 manufacturing.ts 目前为空批次；trade.ts 仅巫恋／孑两条 OperatorCuration。
- **跨设施提醒**：组合普遍跨设施，单一批次无法承载整个组合；每条备注只落对应成员卡，不做「组合级」汇总登记。
- **多设施与已有备注**：同一 operatorId 只能登记一次；多设施成员选与本次协作相关的批次归位，合并其已有备注，不能在多个批次重复登记（重复会触发校验抛错）。
- **内容**：指向式优先，例如「本卡属『红松骑士团组』，完整形态还需与控制中枢侧的薇薇安娜（骑士阵营）配合；技能数值见其卡」。避免在本卡复述他人技能数值。
- **复述数值**：仅在有明确一致性与复核手段时允许；operator 备注没有指纹保护，复述易随 references 变更静默漂移。
- **来源**：references 或 guides 的路径与具体小节记在对应 curation 的中文注释及审计结果中，运行时备注只保留协作导航与必要条件。
- **数量与角色**：按来源区分核心、增强和开放适配成员；人数注明设施范围及是否包含核心。水月按上节文案引导搜索精确词条「标准化类技能」，不将同名技能的未解锁档当作已生效。
- **文案形态**：水月保留搜索「标准化类技能」的明确引导，允许等价措辞调整，不退回只有条件、没有查询入口的描述。

## 实施方案

按依赖顺序执行。步骤 1、2 是内容定稿前置，步骤 3 起为代码/测试/文档落地。

### 步骤 1：逐入口审计（前置）

输入：bench/src/facts/curation/terms.ts、bench/src/facts/store.ts、knowledge/guides/贸易站组合.md、knowledge/guides/制造站组合.md、knowledge/guides/跨设施组合.md。

输出：覆盖 19 个 combo 全部已列入口的审计结果（记入本计划的 notes）：每个入口的命中路径与返回卡集合、每张可承载卡的成员身份与角色、开放范围、该入口已有导航线索、拟补文案、来源小节。

- 本轮范围固定为候选清单写明的入口、19 个正式组合名及其余 3 组核心干员正式名；先在审计结果中去重列出，不扩展所有成员名与问法的排列组合。范围外入口记为未覆盖。
- 对每个入口区分「零命中」「返回但非成员」「成员未返回」三种情况，不把指定入口的覆盖外推为组合级无缺口。
- 每个需补入口选定至少一张有成员依据的返回卡承载导航；已有线索充分时不重复添加，不要求每张返回卡复制同一段备注。
- 列出同一 operatorId 的承载卡冲突清单（在 ≥2 个组合中需承载，或已存在于 trade.ts），作为步骤 3 的合并依据。
- 成员身份以 guides 与 terms.ts 登记为准，开放组合不按显式名单排除可适配成员。

验收：候选清单 15 组＋水月＋其余 3 组全部有审计结论；冲突清单完整；不遗留「未核查即认定不需要」。

### 步骤 2：文案定稿与落位

输入：步骤 1 审计结果、候选清单、备注书写规范。

输出：每条备注的最终文案与落位批次。

验收：每条文案含「组合关系＋目标成员或精确技能组词＋必要条件」，来源按备注书写规范落位；不复述他人技能数值；增强成员不写为启动必需；水月保留搜索引导；开放组合按人数与解锁条件表述。

### 步骤 3：实施 operator notes

输入：最终文案。

输出：在对应设施 curation 批次新增 OperatorCuration（control.ts、manufacturing.ts 等）；跨组合重叠或已有备注合并为一条、单次登记。

验收：`validateCurations` 通过，无重复 operatorId、无孤儿；落位批次与备注书写规范的约定一致。

### 步骤 4：测试同步

输入：bench/tests/curation.test.ts 及现有投影、facts 查询测试。

输出：更新硬编码断言——当前该测试断言 `validated.operators.keys()` 恰为 `['孑', '巫恋']`，新增备注后必须同步为实际集合（或改为按新增内容断言）。

在现有测试中补少量代表用例：通过真实 curated 投影与 facts 序列化确认新增导航可见、增加备注前后命中集合与路径不变；如涉及已有备注，确认原内容仍保留；水月输出包含精确搜索词、另配两名及含水月共三人同站的条件。不复制整份文案做快照，也不新增通用校验机制。

验收：`pnpm run typecheck`、`pnpm run test` 全通过。

### 步骤 5：工程文档收束

输入：本计划、实施 notes、docs/inbox.md。

输出：补齐实施记录并按实际结果勾选工程验收项，更新 inbox 的工程完成状态。原草案删除与 inbox 路由已在转计划时完成，不重复执行。

验收：文档与实际交付一致，运行 `node scripts/doc-check.mjs` 核对引用与结构；施工期间仅由本计划未完成项引起的 D1 如实记录，不虚勾。工程清单全完成后重新运行 doc-check，须完整通过。

归档和合并门禁放在后续发布收束流程：全部工程验收完成后，按 docs/rules/document-lifecycle.md 经 `release/archive-plan` 归档，再执行 `node scripts/verify.mjs merge -- --base main`。不将「归档后门禁通过」列为归档前的 checklist 条件；本计划不执行合并或发版。

### 后续效果验证（另行授权，不阻塞工程交付）

效果试验由 docs/inbox.md 另行路由 exp，使用 docs/templates/exp.md 记录过程、结果与结论，不作为本计划的必达清单项。

若与本轮实施衔接，须在步骤 2 文案定稿前固定未用于修改的验证问题；未提前保留则如实说明，不能把已用于修改的案例事后称为留出集。同一组合换问法仅检验措辞适应性，不据此宣称跨组合泛化。

## 验证方法（可泛化）
