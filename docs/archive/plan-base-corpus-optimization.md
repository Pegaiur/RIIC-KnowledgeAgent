# base 机制语料增量优化计划

> 创建日期：2026-09-03
> 修订日期：2026-09-04
> 状态：已完成
> 上游：`docs/archive/plan-rag-prose-cleaning.md`（base/guides 清洗与白名单切换已完成）
> 相邻但不重叠：`docs/archive/plan-agent-facts-knowledge-layering.md`、`docs/archive/plan-rag-facts-quality-loop.md`（facts 分层、答案基线与评测闭环）

## 目标

在不重写已审定 guides、不复制 references 技能事实的前提下，优化 `knowledge/base/` 的机制语料：

1. 修正标题层级和切块语义，使每个机制块具有稳定、可辨识的检索锚点。
2. 对现有设施机制文做增量补缺和边界澄清，不重复已经落地的表格事实。
3. 从 `knowledge/raw/心情消耗恢复与工休时间.md` 中核验并提炼通用的心情、工休与班次机制。
4. 补齐当前 base 缺失的后勤技能结算规则，使机制说明与 references 的技能原文各司其职。

本草案只交付可进入 RAG 白名单的 base 机制文及其结构性验证，不以完成 20 题答案质量闭环为验收目标。

## 当前状态与问题

- 当前白名单已有 9 篇 base、14 篇 references 和 5 篇 guides；散文层并非待整体重建。
- `knowledge/raw/` 是未审定输入区，默认不进入 `knowledge/corpus-manifest.json`。本轮只消费已明确列入范围的心情与工休材料，不默认消费其他历史推荐或实现文档。
- 八篇 `机制-*.md` 首行使用二级标题，而切块器只从一级标题提取文档名锚点，导致这些机制块没有设施级 `anchor`。
- 多篇设施文的主要正文块同名为「公式与规则」，检索时只能依赖正文词元，设施主题和具体问题边界不够稳定。
- F01-F07 的基础参数已大多落地；继续按旧草案整篇重写会重复现有内容，并容易把技能个例或推荐判断混入 base。
- F08 工休与班次、F10 后勤技能结算仍缺少经核验的独立机制文；F09 同时包含通用解锁语义和培养判断，需要拆分职责。

## 与相邻草案的边界

### 本草案负责

- `knowledge/base/` 的标题层级、自然标题切块、内容去重和机制解释。
- 机制基础参数、通用公式、计算顺序、适用条件和容易误读的边界。
- 指定 raw 材料的逐条核验、提炼、拆分与未采纳结论。
- 新增或调整 base 文件后同步维护 `knowledge/corpus-manifest.json` 及语料结构测试。
- 使用本地 BM25 对 F01-F10 做检索定位冒烟，只检查目标机制块是否可检索，不评价模型答案。

### 后续知识分层与质量闭环计划负责

- F/G 参考要点与陷阱点重制、`docs/spec/rag-answer-baseline.md` 版本递进。
- Skill/Grant/Operator notes 模型、facts curation、指纹与输出预算。
- `facts-notes-review.json`、来源冻结、全量适用性判定与覆盖证明。
- 12+5 查询/裸查对照、人工答案判定、成本统计和 v3 结论。

### 两份草案均不在本轮处理

- references 上游补源、解析器再生或机械字段修订。
- 真实 LLM 20 题运行及 Agent 工具路由质量闭环；该需求由 `docs/inbox.md` 的独立条目承载。
- 完整组合成员表、组合总效率、缺员降级路线、培养优先级和体系评价；这些内容保留在 guides。

## 内容边界

### base 可以承载

- 不依赖具体账号或推荐立场的稳定机制规则。
- 能由 PRTS 机制页、references 原文或明确的数学推导支持的公式与边界。
- 为理解技能原文所需的通用结算语义，例如作用顺序、上限与效率的区别、清零或取最高的适用层级。
- 使用已核验参数给出的短例子；例子必须标明前提，不得反向成为新的事实真源。

### base 不承载

- 干员技能效果数值、持有者枚举、解锁门槛和派系成员表；这些以 references 为准。
- 「首选」「不建议」「必练」「质变」等推荐判断；这些属于 guides。
- 完整组合配置、总效率档位和缺人路线；这些属于 guides。
- raw 中尚未核验的案例、经验结论或排班优劣判断。
- 为 facts 编写的局部语义备注或 curation 文本。

## 实施方案

### 1. 修复 base 的文档锚点与切块

- 八篇 `机制-*.md` 使用唯一的一级标题作为文档主题，保证切块器能生成设施级检索锚点。
- 将大而同名的「公式与规则」表按真实语义拆成自然标题，例如「效率与心情」「订单生成」「线索交流」「等级参数」；不为了切块机械拆散同一条公式的条件与结论。
- `机制-基建总览.md` 只保留跨设施通用概念和入口，不重复发电站、制造站等设施文已经完整说明的机制。
- 保持标题稳定；若必须改名，同步更新依赖该标题的检索测试或定位引用。

验收：所有白名单 base 文件均有非空文档锚点；同一主题的条件、公式和限制位于同一可独立理解的块中；不再依赖多个同名「公式与规则」块区分设施。

### 2. 收口 F01-F07 的存量内容

现有内容以核查和小幅补强为主，不做整篇重写：

- **F01 发电站**：核验并明确充能公式的加成口径；消解旧稿「多站独立结算」与当前「所有发电站加成求和」之间的歧义；说明达到上限后充能、工作状态与心情是否继续。
- **F02 制造站**：保留 `1+X+Y`、仓库容量和心情消耗结构；只补充「每人 +1%」与旧称「满员 +3%」的等价或差异边界，不复制技能类型和槐琥原文。
- **F03 贸易站**：保留订单上限、贵金属分布和特殊订单；补充「订单上限不等于订单获取效率/处理速度」及订单确定时点的解释，不复制具体干员技能数值。
- **F04 会客室**：核验并补齐线索交流期间的搜集状态、传递是否消耗线索、传递限制等通用机制；组合与推荐判断不进入 base。
- **F05 办公室**：保留单人工位、刷新基础时长和等级参数；如加入时长示例，必须明确基础 +5%、技能加成和上限状态等前提。
- **F06 控制中枢**：保留每名工作干员提供的全局心情减免、电力、降级、副手和席位规则；派系、具体全局技能与组合排班不在此复制。
- **F07 心情与宿舍**：整理工作消耗、控制中枢减免、设施减免和宿舍恢复之间的通用关系；具体干员额外消耗或恢复只通过 references 查询，不写成 base 枚举表。

验收：每一项新增陈述都有明确来源或可复算推导；技能事实与推荐判断没有从 references/guides 复制到 base；已存在事实不因改写发生数值漂移。

### 3. 从 raw 提炼心情、工休与班次机制

唯一批准的 raw 输入为 `knowledge/raw/心情消耗恢复与工休时间.md`。处理时逐段标记为「纳入」「仅作例子」「不纳入」：

- 核验工作消耗 `x`、休息恢复 `y`、可工作时间 `24/x`、恢复时间 `24/y`、工休比 `y/x`、最大工作占比 `y/(x+y)` 和每日最长工作时间 `24y/(x+y)` 的定义与前提。
- 将组合可持续时间受最快心情消耗者、宿舍容量和换班频率约束，表述为条件模型，不写成无条件排班建议。
- 16/4/4、8/8/4/4、12/12/12、12/6/6、24/24/24 等案例逐一复算；无法证明其阵容、恢复或产出前提的，不进入白名单正文。
- 具体干员的心情效果回指 references；组合角色和排班建议回到 guides，不在机制文中展开。
- 根据内容耦合度决定落入现有 `机制-宿舍.md`，或新增一篇职责单一的 `机制-心情与工休.md`；不得把整份 raw 原样转正。

验收：进入 base 的每个公式都列出变量定义和适用前提；案例结论可复算；未采纳内容保留在 raw，不因本轮处理获得权威地位。

### 4. 补齐通用解锁语义与后勤技能结算

- **F09 通用解锁语义**：只说明 `精零/精一/精二/30 级` 的读取方式，以及一至二星 30 级、三四星通常精一的常见口径；具体持有者和解锁门槛继续由 references 提供。「精一到精二质变清单」属于培养判断，不进入 base。
- **F10 后勤技能结算**：在来源充分后新增独立机制块或 `机制-后勤技能结算.md`，说明全局资源、固定加成、跨设施影响、容量/上限、差值与他人效率、清零/归零、订单类型、心情效果之间的结算关系。
- 九步顺序不得直接从旧散文恢复为权威规则；每一步必须区分「已有机制来源」「由技能原文可确定」「仍待验证」。无法确定统一顺序时，改写为已确认的局部先后关系，不伪造完整算法。
- 归零、取最高、清除自身影响等术语必须写清作用对象和作用域；具体干员仅可作为带来源的短例子。

验收：F09 不再夹带培养名单；F10 的每条结算关系均可定位来源，未确认关系明确留在草案或 raw，不进入白名单。

### 5. 白名单与确定性检索验收

- 只有完成人工通读和来源核对的新增 base 文件才能加入 `knowledge/corpus-manifest.json`。
- 同步更新语料白名单测试、标题/锚点测试和必要的检索回归夹具。
- 对 F01-F10 的固定问题执行本地 BM25 定位冒烟，记录目标 base 块在 top 5 中的命中情况；失败时优先调整标题、块边界和重复内容，不为命中率堆砌隐藏关键词。
- 本步骤不调用真实模型、不判定最终答案正确性，也不改写 `docs/spec/rag-answer-baseline.md`。

验收：白名单文件与测试一致；F01-F10 中存在 base 机制依据的题目能够定位到相应机制块；`pnpm run check:prose-terms`、`pnpm run typecheck`、`pnpm run test` 和 `node scripts/doc-check.mjs` 全部通过。

## 意外发现
> 实施中发现的 spec 未覆盖的依赖、边界或风险

- `splitChunks` 仅消费 `##`/`###`，H1 只作为 `anchor`；因此自然标题必须使用 H2，H1 不能替代块标题。
- 旧 base 中“技能维度数值”注释本身会把具体技能个例和过时的术语带入玩家侧扫描；已改为只指向 references，避免与技能真源和术语检查冲突。
- raw 案例复核结果：16/4/4 中 A/B 为 20 小时工作、4 小时休息，C 为 8/16；若 8/8/4/4 只是前者拆分，合计不变；按同样的三组轮换解释，12/12/12 为 24/12，12/6/6 为两组 18/6 与一组 12/12，24/24/24 为 48/24。上述算术不证明具体阵容、容量或产出，故全部标记为“仅作例子”并排除白名单。
