# 共享基准快照更新与淘汰计划

> 创建日期：2026-09-06
> 状态：施工中
> 工作分支：`feature/temp-cleanup`

## 目标

落实「严进宽出」：只有明确支撑正式结论的运行进入 Git；失去当前用途的快照随收尾退出当前目录，以 Git 历史保留证据，不为淘汰增加状态协议或等待周期。

## 非目标

不做定时任务、按天数或最近 N 份淘汰、中央注册表、生命周期 JSON、归档子目录、远端状态查询、自动删除系统、通用 Markdown 依赖解析器、LFS 或 Git 历史重写。不发起付费补测，不将模型答错视为必须修复的缺陷，不批量入库其余历史运行。

## 架构分析

已有每 run 单 JSON、bench export/report/compare/validate、清理 JSON 清单与 release-workflow。现有 4 份快照合计 321,911 字节（约 314 KiB）。缺口是入库选择、基线更新和旧快照退出规则；删除当前 JSON 不缩小完整 Git 历史，必须把筛选放在入库前。

2026-09-01T12-06-28-412Z 是 20 题 failed 的失败对照；2026-09-05T10-59-42-129Z 是 20 题 completed 的旧实现基线；10:51、10:54 两份分别是 2 点、5 点预算实验。用途根据实际记录判定，不能只看默认配置、文件名或时间。

## 实施方案

### 1. 入库与保留规则

在现有 `docs/rules/document-lifecycle.md` 定义规则，`skills/release-workflow/SKILL.md` 只承载收尾时机和操作，`scripts/INDEX.md` 补必要用法引用，不复制多份规则正文。

- **严进**：入库前在对应 spec 或 plan/notes 说明该运行支撑什么结论、为何需要它。dry、探索性探针、重复调试默认不入库；不能因是真实请求就永久保存。支撑结论的失败对照必须保留；若结论涉及稳定性或重复实验，相关样本整体保留，禁止只筛成绩好的运行。
- **宽出**：保留者说明当前用途，失去用途即随正常收尾提交移除。当前用途限当前基线、直接比较需要的对照、未结束任务的必要证据；上一基线不是永久保留名额。没有活跃引用的历史结果无需另设淘汰审批、等待天数、最近 N 份或新旧一一对应的替换协议。
- 历史文档提到过某 run 不代表它必须永远留在当前目录。闭合其历史定位即可淘汰；不要为满足引用检查把旧结论改指新结果。
- 每次新增时同步看旧快照去留；净新增在已有结论记录中简述用途即可，不增加逐 run 状态台账。

### 2. 声明与更新当前基线

在现有对应 spec 用普通 Markdown 声明当前 run 路径及用途，阶段实验继续使用 plan/notes。没有足够既有评测依据时明确写「当前未指定正式质量基线」，列明候选用途；不为完成文档动作擅自指定、重跑或优化。避免混淆答案核查标准与实际运行成绩，若使用现有回答核查 spec，独立短段说明运行参考。

新运行新增 run-id JSON，并在同次提交更新当前引用与对比结论。旧运行事实不改写成新成绩；若导出错误需要更正，说明原因并审查普通 Git diff。复用现有幂等、冲突和 schema 校验，不增加替代关系字段。

### 3. 历史定位与本机清理衔接

淘汰前为仍需查阅的历史结论使用「实际包含该 JSON 的完整提交号＋仓库相对路径」。用 `git show <commit>:<path>` 验证可取得文件内容即可，不扫描全部历史、不要求当前工具永久兼容旧 schema。未来 schema 不兼容时使用对应提交的工具。

活动文档随淘汰更新定位；已冻结文档不批量改写。若归档提交含文件，可从该提交复核；若文件后来才入库，或文档归档与快照淘汰同次提交，应在尚未冻结的记录中明确含文件的提交定位。已有冻结文档所缺定位可在本次收尾记录补一句映射，不新增历史索引。

清理器仍要求 snapshot 当前存在、已提交且干净。仅对本次已选入清理清单且仍依赖该快照的原件，先按既有流程完成共享和原件清理，再淘汰快照；可留到下次收尾，不为此专门发版。不要求所有协作者证明本机已清理，不让未知本机存量成为 Git 快照永久保留理由。以后恢复旧清单时可先从历史恢复对应 JSON 并按既有提交/校验流程处理，不新增远端或历史查询机制。

本次实施不执行生产临时文件删除，也不合并、推送或发版。可移除已确认不再需要且未被本次待执行清理清单依赖的已跟踪快照（普通 Git 变更，可审查）；其他快照明确本次保留用途即可。

### 4. 复用统计与处理现有存量

在 `bench/src/benchmark-integrity.ts` 的现有快照枚举中累加总字节，在现有 validate 输出中与 snapshotCount 一起展示；不新增入口、依赖或第二轮扫描。统计提供可见性，不增加数量/体积硬门槛。取消当前至少一份快照的限制：目录缺失或没有 JSON 时返回 0 份、0 字节，允许最后一份失去用途后退出；存在 JSON 时仍逐份严格校验。空集合不代表活动引用自动有效，收尾仍核对当前文档引用。

审定现有 4 份的用途和去留，纠正活动记录中的用途混淆。2 点、5 点及旧实现仍是当前预算比较证据；失败对照是否保留根据当前引用与任务用途判断。其余 44 个真实运行不整批提取，后续按严进入库规则处理。结论和去留写入既有文档，不为每 run 新建文件。

### 5. 验证与收束

使用隔离样本验证一次新基线入选、旧基线淘汰、历史 JSON 恢复与报告读取；校验当前引用有效、恢复前后数据一致。复用已有测试扩充有意义的统计断言，不为自然语言规则建立解析测试。实际数据只做校验，不付费跑测或删除原件。

运行 typecheck、test，先 `pnpm run build` 再执行 `node dist/cli.js validate`，并运行 doc-check；实施完成后勾选实际通过项，再执行统一合并门禁。计划阶段的 D1 未完成项如实保留，不能为了提交实施计划提前勾选。

## 验收清单

- [ ] 当前基线或未指定状态明确；现有 4 份用途、保留或淘汰结论可查，不扩展历史批量入库。
- [ ] 隔离样本验证基线替换、当前引用、历史提交恢复及报告读取；归档同次淘汰和后补证据的定位有明确操作约定。
- [ ] 本机清理依赖只约束本次显式清单，不要求多人清理同步；既有清理保护保持有效。
- [ ] validate 复用现有枚举输出快照数和总字节，覆盖空集合与非空统计；已有 JSON 仍严格校验。
- [ ] typecheck、test、bench validate、doc-check 与统一合并门禁通过，未付费补测、未删除生产原件。
