# Agent 单请求执行与成本模型评估

> 创建日期：2026-09-05
> 状态：评估完成，迁移方向待定
> 入口：`docs/inbox.md`「Agent 单请求执行与成本模型评估」

## 结论

当前实现确实在客户端逐轮调用模型，但这是标准的 Function Calling Agent loop。需要区分三件事：用户提交一次问题、客户端向模型服务发送一次 HTTP 请求、模型服务只执行一次生成。这三个计数不等价。

最接近“一个模型 API 请求内自主检索并继续回答”的候选是 **百炼 Responses API + 远程 MCP 工具**。官方当前列出的支持模型包含 `qwen3.7-flash`，无需先更换模型。但托管循环不等于中间过程免费，也不能仅凭客户端请求数下降推断总费用下降。[模型与协议支持](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-responses)、[MCP 调用与计费](https://help.aliyun.com/zh/model-studio/mcp)。

建议将该方案作为满足目标形态的候选，以当前本地循环及其缓存优化版作对照。若核心要求是每题只进行一次模型生成，则应另选“本地先检索、模型一次作答”；它不具备模型看到工具结果后自主追加查询的能力。当前证据还不能确定哪条路径成本更低且质量不退步。

本次完成源码核查、官方文档调研和已有账本离线复算；未执行迁移或新增真实模型请求。

## 现状与开销来源

主要代码位置：

| 位置 | 实际行为 |
|------|----------|
| `bench/src/agent.ts:188` | 循环上限为 `maxRounds + 1`；当前默认最多 4 次逻辑模型调用 |
| `bench/src/agent.ts:206` | 每轮调用 `callLLM(messages, offeredTools, ...)` |
| `bench/src/agent.ts:252`、`:358` | 将工具调用及工具结果追加到 messages，下一轮重新发送 |
| `bench/src/provider.ts:35`、`:79` | POST Chat Completions；固定非流式，有工具时 `tool_choice: auto` |
| `bench/src/agent.ts:193`、`:386` | 只有兜底轮撤掉工具；未先检索的回答可能被丢弃，再要求检索 |
| `bench/src/pricing.ts`、`bench/src/report.ts` | 按每次响应的 usage 算费并累加，缓存命中采用仓库隐式缓存价格 |

工具由本地 TypeScript 执行；发送给模型的 function schema 只是工具名称、说明与参数，未包含可由服务端执行的函数实现。官方流程同样要求应用执行工具，再携结果发起后续模型调用。[Function Calling 工作原理](https://help.aliyun.com/zh/model-studio/qwen-function-calling)。

以两次依赖前一结果的检索为例，简化为：

```text
第 1 次：规则 + 问题 + 工具定义                         → 查询参数 A1
第 2 次：规则 + 问题 + 工具定义 + A1 + 结果 T1          → 查询参数 A2
第 3 次：规则 + 问题 + 工具定义 + A1 + T1 + A2 + 结果 T2 → 最终答案 F
```

重复历史主要增加输入；正常工具轮输出的是参数及可能的伴随正文，不是每轮都生成一份完整答案。工具返回文本本身来自本地，其 LLM 费用体现为后续输入。真正可避免的完整输出浪费之一，是最少检索约束丢弃的提前回答。

`stream: true` 只改变当前接口的响应传输方式；把循环装进 SDK 或本地 `/ask` 接口也只改变封装边界。它们本身不能消除底层推理与 token 费用。模型必须收到真实工具结果后，才可能据此选择下一步；只用提示词模拟工具结果不能替代知识库执行。

## 已有实验复算

范围为 2026-09-05 的六轮温度实验，0.2 与 0.7 各三轮，每轮同一套 20 题，均为 Qwen3.7-Flash/off/hybrid。这里合并用于描述工作负载，不用于比较温度优劣。

| 指标 | 六轮合计 |
|------|---------:|
| 已完成查询 | 120 |
| 有记录的模型响应 | 286，平均 2.38 次/题 |
| 每题调用次数分布 | 2 次：83 题；3 次：28 题；4 次：9 题 |
| 输入 token | 465,284 |
| 缓存命中输入 token | 43,008，占 9.24% |
| 全部输出 token | 109,506 |
| 最终答案输出 token | 90,149，占全部输出 82.32% |
| 提前生成后被丢弃的回答 | 12 次，13,193 输出 token |
| 仓库账本总费用 | ¥0.173788，约 ¥0.028965/20 题 |
| 非最终模型响应的账本费用 | ¥0.051724，占总费用 29.76% |

费用采用现有仓库价格和每次调用的小数舍入规则，不是阿里云账单对账结果。`costIn` 与 `costOut` 分别累加后，与独立舍入的 `costTotal` 可能有微小差异。

**29.76% 是历史非最终响应的费用占比，不是迁移可节省比例或上限。** 单次生成可能需要不同的检索材料；托管循环仍有内部生成；新路径的缓存命中、最终输入和答案长度也会变化。不能删除历史前几条成本记录，再把最后一条当作新方案报价。

首轮输入为 1,039–1,060 token，但这包含工具定义、问题等，不能证明 system 消息单独达到显式缓存的最小前缀长度。应检查实际可缓存的完整前缀位置，不能为凑阈值填充无用文本。

复算入口：`node dev-temp/agent-loop-evaluation/analyze.mjs`。脚本逐条核对 trace usage 与 records，以每题最后一条无工具且有正文的响应归类最终答案；目录映射及明细在 `dev-temp/agent-loop-evaluation/results.json`。这些是已有题目的重复运行，未新增完整答案盲评，也不能从“执行完成”推断答案正确。

现有 `records` 记录成功返回 usage 的逻辑模型响应；`fetchWithRetry` 可能产生更多 HTTP 尝试。历史记录无法证明超时请求未在服务端执行或计费，因此 286 不应标成实际网络尝试数。

## 候选方案比较

| 方案 | 客户端到模型服务的请求 | 模型根据工具结果追加查询 | 工具执行位置 | 修改量与主要取舍 |
|------|----------------------|--------------------------|--------------|------------------|
| A. 当前循环 + 请求阶段约束 | 通常 2–3 次，异常路径受现有上限控制 | 保留 | 本地 | 小；消除部分无效轮次，不能满足单请求形态 |
| B. 本地循环 + 显式/会话缓存 | 仍有多次 | 保留 | 本地 | Chat 显式缓存为较小改动；Responses 会话缓存为中等改动，均需更新计费 |
| C. Responses + 远程 MCP | 正常路径一次 Responses 请求 | 服务端托管 | 百炼可访问的 MCP 服务 | 中到大；最符合预期，增加部署、运行控制与观测迁移 |
| D. 检索前置 + 一次生成 | 一次 | 生成期间不能再查 | 本地，调用模型前完成 | 中；减少模型往返，但取证策略改由程序决定 |

### A：作为现有控制流的改进

已有 [请求阶段工具约束计划](plan-agent-tool-request-policy.md) 覆盖额度耗尽后撤工具、Qwen off 首检 required。它能减少提前回答和预算拒绝导致的浪费，仍是客户端 Agent loop，不能作为本次“单请求执行”需求已完成的依据。

单个模型响应可提出多个工具调用；本地也已遍历执行它们。对互不依赖的查询，一次提出全部工具请求有机会减少模型轮次，但执行后仍需模型读取结果。依赖 T1 才能确定 A2 的情况不能无条件并行。

### B：保留本地工具，直接优化重复输入费用

有两条不同路径：在当前 Chat Completions 中标记显式缓存前缀；或迁移至 Responses，用 `previous_response_id` 关联历史，并启用 `x-dashscope-session-cache: enable`。后一条仍需将本地 function 的执行结果发回模型，不是单请求托管。会话缓存默认关闭，支持显式缓存时采用显式缓存规则。[Responses 会话缓存](https://help.aliyun.com/zh/model-studio/compatibility-with-openai-responses-api)。

Qwen3.7-Flash 当前在显式缓存支持列表中。该缓存要求至少 1,024 token；创建按标准输入价 125%，命中按 10%，5 分钟未复用会过期；隐式缓存对应命中价为 20%。[缓存规则与计费](https://help.aliyun.com/zh/model-studio/context-cache)。

因此必须同步更新 `provider.ts`、`types.ts`、`pricing.ts` 及账本输出：保留缓存创建量，区分显式与隐式命中，按接口实际返回字段和账单口径映射。在仓库当前输入价 0.2 元/M 的前提下，显式创建价为 0.25 元/M、命中价为 0.02 元/M；不能继续将所有缓存命中按 0.04 元/M 计算。

短循环可能只复用前缀一次，最后作答轮新建的缓存也可能没有后续使用；缓存创建溢价、前缀长度、工具集变化、跨题可复用部分都影响收益。当前低命中率提供了调查理由，但不能承诺启用缓存一定更便宜。

### C：实现用户预期的托管流程

```text
本地发起一次 Responses 请求
  → 百炼模型选择工具
  → 百炼访问 MCP，取得 rag_search / lookup / query_operators 结果
  → 百炼继续生成，必要时再次调用 MCP
  → 同一响应返回最终答案与公开执行记录、usage
```

这需要将现有检索与 facts 能力提供为服务端可访问的 MCP。当前百炼文档要求 SSE MCP 服务端点；本机函数或 stdio MCP 不能直接充当这个远程端点。费用仍分模型 token 和 MCP 服务费用。[MCP 接入](https://help.aliyun.com/zh/model-studio/mcp)。

具体迁移内容：

1. 从 `agent.ts` 提取本地工具执行与结果组装，复用 `retriever.ts`、`facts/store.ts` 和相同知识快照；在 MCP 中暴露相同三个只读工具。若要维持现有 BM25/facts 语义，不直接换成供应商内置知识库搜索。
2. 增加 Qwen Responses 适配：请求、输出 item、usage 和失败状态都与现有 Chat 格式不同。`provider.ts` 目前读取 `choices`、`prompt_tokens`，不能只替换 URL；Hy3 对照继续使用其原有适配。
3. MCP 请求必须能归属到具体查询，服务侧执行相同工具预算并记录实际参数、命中和返回文本。工具预算只能限制执行，不能证明模型不会继续尝试调用；当前本地撤工具和兜底机制需要重新设计并验收。
4. 保留 Responses 返回的公开 MCP 事件和最终 usage，并与 MCP 执行日志关联。报告分清外层请求、可观察模型步骤和实际工具调用；若内部步骤数未公开，应标为不可观察，不能将外层一条记录标成一次内部推理。
5. 明确 MCP 托管方式、知识快照同步、认证、每题隔离及超时行为。这会改变仓库“仅本机运行”的部署边界，选定后应先写 ADR，再转实施计划。

公开 Responses 参数表未列出 `max_tool_calls`，并明确未列参数会被忽略；不能照搬其他厂商的同名参数来声称已保留轮次上限。[Responses 兼容性说明](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-responses)。

**尚待协议小样与账单确认的事项**：当前账号端点上的模型/MCP组合行为、非思考路径是否按预期多次取证、工具预算与终止方式、内部各步输入如何累计或缓存、缓存创建量如何返回、超时后的执行与费用归属。文档说明其按 token 收费，没有承诺“一个响应内历史只计一次”或“工具调用参数免费”。不根据客户端封装或未公开的 KV cache 实现作出降费承诺。

### D：真正限制为一次模型生成

程序先按题目原文跑 BM25；对明确的标准干员名、技能名、设施或阵营，复用已核验索引做 facts 查询，再去重并限制总证据量。模型只接收规则、问题和证据包，不提供待执行工具，生成一次最终回答。

需要处理泛问、别名歧义、组合成员发现和跨片段关系。`facts/store.ts` 已注明别名与合称索引尚不完整，不能假定已有完整实体解析。提前检索若用另一 LLM 生成查询，则整体已经多于一次模型生成；若复制历史 Agent 的查询词，则只能作为事后证据对照，不能计作可独立部署的方案。

主要涉及 `agent.ts` 或独立执行入口、证据组装、runner 的执行模式元数据，以及共享 `knowledge/AGENTS.md` 对预取证据的适配。规则仍维护单一人工来源，不能另造一份作答规则。证据不足时输出有依据的局部答案及缺口；若增加补查回退，应单独记录为多次生成路径，不能继续标成严格单次。

## 建议的验证与决策顺序

1. **固定基线**：保存包含当前未提交温度接线的源码快照、问题、语料、指令哈希、完整配置与价格版本；不能仅以 HEAD 代表当前实现。对照用 Qwen3.7-Flash/off/hybrid、显式 temperature=0.7，其余沿用现有参数。
2. **隔离协议与缓存收益**：先比较当前 Chat 路径与只增加显式缓存的路径；若采用 Responses，则先保留本地工具，分别检查不开会话缓存与开启会话缓存。不要把工具策略、缓存、远程部署、回答约束一次叠加后归因给单请求。
3. **托管候选小样**：C 先用 F06、F09、S02、S03、S05、G02 检查预算耗尽、提前回答、facts 分类、组合及泛问；另设确实需要先查后决定下一次查询的固定工具场景，验证依赖执行而不只验证同轮多调用。必须同时拿到外层响应和 MCP 执行日志。
4. **单次生成对照**：D 使用题目原文与通用规则独立取证，不能使用题号、gold 或历史模型查询词路由。离线覆盖只用于筛选，最终仍需实际生成答案。
5. **按质量和实际费用选型**：通过小样后，以完整 20 题交错重复对照，按 [答案核查基线](spec/rag-answer-baseline.md) 核查必要内容、事实错误和无依据补写。同步报告截断、缺答案、模型/工具调用、输入/输出/缓存创建与命中 token、总费用及耗时；费用下降不能由拒答增多换来。

采用 C 的前提是：确实保留自主依赖检索，单次外层请求可完成，知识版本与工具结果可审计，查询预算可落实，质量无未解释退步，计费口径可对账。若只达成外层单请求而未改善费用，应明确报告“形态达标、降本未证实”，再决定部署成本是否值得。

本草案补充已有工具约束计划的架构评估，不改变其验收状态。缓存可先作为本地循环优化研究；C 与 D 改变执行或部署边界，方向选定后按仓库规则记录 ADR 并形成 plan。
