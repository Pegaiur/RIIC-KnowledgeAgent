## 决策偏离

### 2026-09-05 — 明确单次回馈的决策来源

- **背景**：独立审查认为单次回馈上限合理，但 ADR 原措辞容易把具体次数归为用户明确要求。
- **选项**：维持模糊归因，或区分用户确定的回馈范围与实施方案选择的次数上限。
- **决策**：采用后者；已回馈 ADR-005，行为不变。
- **影响**：固定 auto 和正常工具循环保持原决策，单次回馈的理由可独立复核。

## 实现调整

### 2026-09-05 — CLI 解析与配置校验拆分

- **spec 原文**：配置默认 5 点、正整数总超时，`--min-rag 0|1` 保留兼容映射。
- **实际做法**：将 CLI 解析抽到 `bench/src/cli-args.ts`，数值缺失保留为 `NaN`，由 `validateBenchConfig` 统一报中文错误；运行配置暂保留旧字段，待主循环迁移阶段删除。
- **原因**：先建立可单测的输入边界，避免 CLI 入口副作用阻碍 TDD；旧字段用于阶段间保持现有测试和运行路径可编译。
- **后果**：阶段 4 替换主循环时必须同步移除 `maxRounds/minRagCalls` 兼容字段及旧测试断言。

### 2026-09-05 — 阶段 1 审查通过

- **范围**：`config.ts`、可测试 CLI 解析器、配置边界测试及运行提示。
- **审查**：本地自审（宿主无可用独立审查型子代理）；核对了旧参数路径、缺失数值的 `NaN` 传播、正整数校验、密钥读取路径和新增输出的敏感信息边界。
- **验证**：`pnpm run typecheck`、`pnpm run test`（25 个测试文件 / 206 个测试）、`pnpm run build`、`pnpm run bench:dry` 均通过。
- **结论**：阶段 1 完成；未勾选最终计划验收项，进入阶段 2「异常记录和整题取消」。

### 2026-09-05 — usage 与失败结果契约调整

- **spec 原文**：失败、中止保留已发生记录；缺失或无效 usage 不得补成零；总超时覆盖请求、重试、等待和后续模型步骤。
- **实际做法**：`LlmUsage` 和费用分项允许 `null`，解析器返回 `complete/partial/unknown`；`runQuery` 返回带 `status`、`terminationReason`、`failure`、真实 `modelSteps` 的结果，runner 按结果收集 records；取消信号贯穿限流、请求重试退避和单题循环。
- **原因**：让失败路径和正常路径共享同一结果协议，避免 runner 通过异常分支把前序事实清零。
- **后果**：报告聚合暂以已知数值求和，未知费用的显式标记留到阶段 5 统一补齐；旧 trace 的 schema 版本仍由读取方兼容处理。

### 2026-09-05 — 阶段 2 审查通过

- **范围**：usage 校验、可空费用、单题超时/取消、失败结果收集、trace 状态和相关测试。
- **审查**：本地自审（宿主无可用独立审查型子代理）；核对了明确零值、缺失字段、显式无效字段、模型失败后的前序 records、工具失败参数保留、超时后不再发起下一模型步骤及取消状态映射。
- **验证**：`pnpm run typecheck`、`pnpm run test`（26 个测试文件 / 213 个测试）通过；阶段 2 未执行真实网络请求。
- **结论**：阶段 2 完成；进入阶段 3「统一 schema 和按批次扣点的工具执行器」。

### 2026-09-05 — 统一工具执行器先行落地

- **spec 原文**：使用唯一 `knowledge(operation, params)` schema；按响应数组顺序预占预算，收齐后按原顺序回写；每个调用均有结果，预算拒绝不执行也不扣成负数。
- **实际做法**：新增 `tool-executor.ts`，将五种检索模式的 operation 白名单、参数校验、RAG/facts 派发、注入 ID 记录、批次预算账本和结果 envelope 收拢到独立门面；主循环保留在下一阶段切换，以便本阶段单独审查扣点边界。
- **原因**：先隔离预算和本地工具语义，避免 schema 迁移与旧 Agent 轮次逻辑同时改变，便于定位回归。
- **后果**：阶段 4 必须删除旧的四个独立工具 schema、接入 `knowledge` executor，并将结果 envelope 原样写入 messages 和 trace。

### 2026-09-05 — 阶段 3 审查通过

- **范围**：统一 schema、五模式白名单、批次预占、边界拒绝、无效调用计点、call ID 协议校验和执行结果序列化。
- **审查**：本地自审（宿主无可用独立审查型子代理）；核对了第 5/6 次边界、响应顺序与完成顺序解耦、未知函数名、参数错误不静默回退、重复/缺失 ID 不执行，以及底层异常的 fatal 标记。
- **验证**：`pnpm run typecheck` 与 `pnpm run test -- bench/tests/tool-executor.test.ts` 通过（9 个测试）；尚未切换生产 Agent 主循环。
- **结论**：阶段 3 完成；进入阶段 4「替换主循环并收窄回馈兜底」。

### 2026-09-05 — 主循环切换与旧兼容入口收口

- **spec 原文**：每次生成固定提供 `knowledge` schema 和 `tool_choice=auto`；工具批次继续由模型决定，直接作答的宿主回馈最多一次；删除按 `maxRounds` 清空工具的路径。
- **实际做法**：`runQuery` 改为无固定轮次上限的持续循环，统一回写 assistant/tool 消息，批次结果直接使用 `tool-executor` 的结构化 envelope；无工具直接作答仅在首次触发一次中文 user 回馈，回馈后仍无工具则以 `no_tool_after_feedback` 未完成。删除旧的四个独立 schema、`MAX_RAG_CALLS`、`maxRounds`/`minRagCalls` 运行字段及旧模型输出兼容转换；dry 轨迹同步改用统一 envelope。
- **原因**：阶段 3 已独立验证预算和分发边界，阶段 4 将真实 Agent 主循环切换到同一执行器，避免生产路径仍保留旧 schema 或轮次兜底语义。

### 2026-09-05 — 阶段 4 审查通过

- **范围**：固定 `auto` 循环、并行工具参数、统一 schema 注入、五次依赖工具步骤、同批调用回写、预算归零后的继续调用、单次无工具回馈、回馈后未完成、截断/重复 call ID/工具失败路径，以及旧轮次和旧工具入口清理。
- **审查**：本地自审（宿主无可用独立审查型子代理）；逐项核对主循环顺序为“保存 usage/费用 → 截断检查 → 批次执行或正文判定”，核对未调用工具与已调用工具的回馈分支、预算快照和失败 trace；`git diff --check` 通过。
- **验证**：`pnpm run typecheck`、`pnpm run test`（28 个测试文件 / 229 个测试）、`pnpm run build`、`pnpm run bench:dry` 均通过；未发起真实网络请求。
- **结论**：阶段 4 完成；进入阶段 5「同步可观测性、报告和 dry 管线」。

### 2026-09-05 — 可观测性与 dry 管线同步

- **spec 原文**：记录模型步骤、工具批次、提出/准入/执行/错误/拒绝、预算前后值、回馈次数、终止原因和结果字符数；meta 固定记录 auto、并行、预算、超时、schema 版本；报告不得把不完整 usage 当作完整零费用。
- **实际做法**：新增 `ToolBatchStats` 并写入每次模型记录；trace 增加工具结果状态、执行标记、余额和单题 summary；runner 的 `meta.json` 增加 schema、生命周期、工具账本、回馈与终止原因汇总，answers 改展示工具批次与预算；report 聚合工具批次和结果字符数，并区分完整/部分/未知 usage，费用字段保持已知小计语义。dry provider 已切换为统一 `knowledge` envelope。
- **原因**：将模型步骤、工具批次和实际 operation 分层保存，既保留外层协议事实，也支持成本/质量复核不把并行批次误当单次调用。

### 2026-09-05 — 阶段 5 审查通过

## 意外发现

### 2026-09-05 — 截断检查与工具执行的优先级存在歧义

- **发现**：原计划同时规定有工具调用就处理批次、截断则异常退出，未明确两者先后。
- **影响**：已回馈 spec：保存响应与费用状态后先检查截断及协议完整性，再准入工具。增加截断响应含合法前缀调用和残缺参数的验收，要求零执行、预算不变、记录保留。

### 2026-09-05 — 成功响应也可能缺少有效 usage

- **发现**：原计划仅明确网络失败时的未知用量；当前解析会把缺失字段补成 0。
- **影响**：已回馈 spec：HTTP 200 同样校验输入/输出用量，保留已知分项，未知部分明确标记，汇总不冒充完整费用；加入缺失、部分、无效和明确零值的验收。仅计量不完整不自动重试模型。

## 阻塞与解决

### 2026-09-05 — 计划提交与合并门禁的范围

- **症状**：正式计划含未完成验收项，文档检查 D1 会报错。
- **根因**：D1 检查的是实施完成和合并/发版条件，当前交付是用户已要求提交的计划与配套笔记。
- **解决方案**：保留真实未完成状态，在功能分支提交文档；不宣称文档全量检查通过，不合并或发版，不修改门禁。
- **预防**：后续完成实施验收并按生命周期归档后，再执行合并门禁。
